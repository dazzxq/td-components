## Decisions

Adopt inventory §9 **D1–D25 as recommended**, with one change to D24 (execution shape, below). Key points:
D1 `TdMenu` is a static helper (`open/close/isOpen/bind/button`) in `src/feedback/`, no `<td-menu>` tag; D2 roving real
focus on `role=menuitem` items (APG Menu Button); D3 share only pure helpers (`utils/typeahead.js`, `placeFloating`),
no shared listbox class; D4 Tab closes the menu and passes (focus returns to the trigger only for selections/Escape that close the menu); D5 outside `pointerdown` closes (no gesture swallowing);
D6 item model (`label`, `onSelect`, `href`/`newTab`, `icon`/`iconNode`, `hint`, `danger`, `disabled`, separators, and
checkable items: plain `<button>`s with `role="menuitemcheckbox"` / `role="menuitemradio"` + `aria-checked`, no nested
controls — this replaces dwp's custom-node theme switch; review ISSUE-2);
D7 `placeFloating` gains an additive `align` option; D8 chip-input submits one FormData entry per item under the host
`name`; D9 `search(query, { signal })` provider with debounce, min chars, AbortController + sequence guard (the dcms
race is not copied) — **`show-on-focus` runs a focus-triggered search with the empty query even when `min-chars` > 0;
typed searches honour `min-chars`; tested (review ISSUE-5)**; D10 `allow-create` + optional `create(text)`, `max-items`; D11 one tab stop + roving among chip
remove buttons; D12 one `role=status` region per host; D13 body-portal strong-glass suggestions popup at
`LAYERS.popover`; D14 `renderOption`/`renderChip` return a Node or TEXT (never HTML); D15 `TdFormValidation` static
class (`validate`, `apply`, `clear`, `attach → detach`) in `src/utils/form-validation.js`; D16 native constraint
attributes are the rules (+ optional JS `rules` via `setCustomValidity`; no data-attribute rule syntax); D17 server
error key → field resolution inside the root only, **followed by one normalisation step (review ISSUE-4): a wrapper match
(e.g. `[data-field]` div) resolves to its descendant `TdFormElement` or native control, and that real control is used
consistently for dispatch, document-order sorting, summary links and focus**; D18 as in the inventory: **`apply()`
(server errors) never changes constraint validity** — td controls get `setError`, native controls get `aria-invalid` +
`aria-describedby` + a `.td-field-error` note; `setCustomValidity` is used ONLY by `validate()` for client `rules`
(review ISSUE-1); server errors clear on `clear()`, on the next `apply()`, and (with `attach()`) when the user edits
that field; D19 focus the first invalid control in document order, optional summary; D20 live
revalidation only after the first failed submit — **the handler resolves the event target to its owning validation
control (normalised as in D17), re-runs that control's custom rule (resetting `setCustomValidity('')` first) before
reading `validity`, then shows or clears the error; tested invalid → valid → invalid for a custom rule on a native input
AND on a `TdFormElement` (review ISSUE-3)**; D21 Vietnamese constraint messages for td-checkbox/td-toggle/td-slider
(fix the English ones); D22 no TdModal change, documented async-save recipe; D23 Vietnamese defaults + site-overridable
`static labels`, fix docs/vision.md:47-48 (Vietnamese defaults; lightweight `TdFormValidation` shipped, not backlog — review ISSUE-8); D25 scope guard as listed.

**D24 (execution) — changed:** same single release v0.12.0, but built like batches 2–4: the lead does the shared step
0, then **three parallel agents in isolated worktrees** (menu, chip-input, form-validation), then one integration and
one Codex impl-review over the whole branch + a security-review (chip-input remote data, FormValidation user input →
DOM). Reason: the slices are independent after step 0 and the batch workflow is proven; a per-slice review loop would
triple the review rounds without new coverage.

**No-glass-on-glass (inventory §6.4):** each floating component keeps its own `:root:has(.td-modal[data-state="open"])`
rule in its own CSS file (the batch-3 convention; no shared list).
