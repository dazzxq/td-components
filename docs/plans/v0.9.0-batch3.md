D16 hoverable, touch-ignored, focus-shown, no auto-hide, `--td-z-tooltip: 510`; D17 dropdown select-only combobox +
non-focusable options + `aria-activedescendant` + clear in the arrow model; D18 dropdown `label` + error contract;
D19 Tab handling; D20 "no glass on glass" via CSS `:has()` on private tokens; D21 modal body is the only scroller;
D22 validated `width/height/bodyPadding` via `CSS.supports` → custom props; D23 datetime-picker harness-only
(`_meta.mixed`); D24 scope guard (no td-menu, top layer, toast position API, multi-select, tooltip delay,
**drag-to-dismiss sheet gesture/API**). **The existing responsive bottom-sheet layout of td-modal below 640 px is
retained** and covered by a viewport test (review ISSUE-3).

**Layer ownership (review ISSUE-1)** — two separate concerns, one registry in `src/utils/layers.js` (+ inert-lock):
- *Inert exemption*: blocking leases (`acquireInert`, layers modal 400 / lightbox 350 / loading 480) inert everything
  below them except elements registered at a higher layer; floating registrations (`registerFloating`, never inert
  anything) exempt their element from LOWER blocking leases only.
- *Keyboard ownership (revised, review round 2)*: registrations declare `keyboard: 'boundary' | 'none'` plus optional
  handlers `onEscape()` / `onTab(e) → 'handled' | 'pass'`. A single capture `keydown` listener in `layers.js`
  walks active registrations **from the highest layer down, considering only `boundary` ones** (toast registers
  `'none'` and is skipped):
  - **Escape** goes to the highest boundary only. It is always consumed there (`preventDefault` +
    `stopPropagation`) — a modal (boundary, Escape intentionally a no-op per ADR 0006) therefore shields a lightbox
    below it; a dropdown/tooltip boundary closes itself.
  - **Tab** goes to the highest boundary; `'pass'` hands it to the next lower boundary (e.g. an open dropdown whose
    focus is on its trigger closes and passes, so the modal trap still wraps at the dialog edges; focus in the
    portaled search input is `'handled'` per D19). Blocking boundaries implement the trap.
  - **Trap scope**: a blocking trap cycles through its own focusables PLUS focusables inside higher registrations
    that opt in with `includeInTrap: true` (toast container), so a toast's close button stays reachable over a modal.
- *Lifetimes*: dropdown menu open → close; tooltip show → hide; toast container first visible toast → last removed;
  modal show → close (per dialog); lightbox open → close; loading show → release. Release is idempotent.
- Tests: loading shown over an open modal holds focus and the modal is inert; Escape on an open dropdown menu over
  a lightbox closes only the menu; Escape with a tooltip over a modal hides only the tooltip; Escape with a modal over
  a lightbox closes nothing; Tab from a dropdown search input over a modal returns to the trigger and the trap still
  wraps; a toast close button is reachable by Tab while a modal is open; release in any order.
