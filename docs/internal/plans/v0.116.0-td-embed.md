# v0.116.0: td embed (ADR 0045), wave 1

Request: btv-custom-rss-full-text (IMS4 editor panel, a Tampermonkey userscript running inside a third-party CMS). The
owner decided that the kit owns and builds the embed, that the panel uses real kit elements, and that the theme switches
automatically.

Both reviews of ADR 0045 are folded in:
- **Consumer review:** CSS ships inside the JS, `rem` is anchored, mount validates before it touches the DOM, unmount is
  idempotent, and the token gate includes the panel's own tokens.
- **Codex review (sol/high):** use a scoped custom element registry, quarantine custom properties, find the press
  target through `composedPath`, drop `contain`, and extract the native-select CSS.

## Goal

- `npm run build:embed` produces `dist/embed/td-embed.js`. It is one minified ES module that is fully self-contained:
  it carries the CSS text, the icon subset, the classes, the mount helper and the build metadata. It also produces
  `dist/embed/td-embed.css`, which is for reading only and is never used at runtime.
- The module exports `mountTdEmbed(host, opts?)`, `TdEmbedError` and `TD_EMBED_BUILD`.
- **What a mount creates:**
  - an open shadow root on `host` with a **scoped `CustomElementRegistry`**;
  - inside that root, `<div class="td-embed-root" data-td-theme="auto">`;
  - a returned handle: `{ root, shadowRoot, registry, create(tag), setTheme(mode), unmount() }`.
- Inside `root`, `td-button`, `td-input-field` (text and textarea) and `td-alert` keep their usual names, look and
  behave as they do in light DOM. They live in the scoped registry, so the CMS page registry is never touched.
- Hostile page CSS does not change these elements, and their CSS does not change the page.
- `select.td-native-select` becomes a new public class: a styled native `<select>` that works without a `td-dropdown`
  parent, both in light DOM and in the embed.
- Light-DOM sites see no behaviour change. `td.css`, `dist/` and every existing test stay green.
- **Browser floor for the embed:** Chrome/Edge 146, Safari 26.4, Firefox 159. Safari 26.4 is the conservative
  choice, because 26.4 fixed the scoped-registry null and initialize cases. Without
  `CustomElementRegistry` construction or `adoptedStyleSheets`, mount throws `TdEmbedError('unsupported')` and the
  consumer falls back to its current integration. The light-DOM kit floor is unchanged.

## Decisions (QĐ)

**QĐ1. No global auto-define in the embed.**
- `td-button.js:510`, `td-input-field.js:1528` and `td-alert.js:174` call `customElements.define('td-*')` when they
  load. New `src/base/define.js` exports two functions:
  - `defineElement(name, cls)`, which runs the existing `if (!get) define`, but only while auto-define is on;
  - `suppressAutoDefine()`.

  The three modules switch to `defineElement`, with no behaviour change in light DOM.
- `src/embed/index.js` imports `./suppress.js` first, which calls `suppressAutoDefine()`, and then the component
  modules. ESM evaluates depth-first in import order, and esbuild keeps that order when it bundles.
- `suppress.js` and `define.js` are leaf modules: they import no component, and there is no top-level await on that
  path. Suppression is one-way for the module instance. It is safe because the embed is a separate bundle that shares
  no module instances with light-DOM entries. `suppress.js` goes into the `sideEffects` allowlist in package.json so
  that it cannot be tree-shaken.
- **Gates (Codex R2):**
  1. Importing the built bundle with a spy on the global registry makes zero global definitions.
  2. A mount defines exactly the three names, in the scoped registry only.
  3. Normal light-DOM imports still auto-register globally.
  4. A static scan of the embed-reachable modules finds no direct `customElements.define(`, only `defineElement`.

**QĐ2. Scoped registry** (`src/embed/registry.js`):
- **Realm:** the registry is constructed from the **page realm**, as
  `new (host.ownerDocument.defaultView.CustomElementRegistry)()`. It is never built from the module's own global. The
  consumer runs in the default Tampermonkey sandbox (`@grant GM_*`, no `@sandbox`). There the DOM and the page's
  `customElements` are reachable, and kit classes already register and upgrade today through
  `document.defaultView.customElements`, but the page's JS globals are not visible.
- The registry is created lazily on the first mount, once per (module instance, Document), and kept in a WeakMap
  keyed by Document. Then `registry.define()` registers the three names with their existing classes.
- A re-injected userscript evaluates a new module and gets a new registry, so there are no conflicts and no build-id
  checks.
- **Feature check**, on the same page-realm object `view = host.ownerDocument.defaultView` (`'CustomElementRegistry' in view`, `view.CSSStyleSheet`, construction succeeds, and `attachShadow` accepts
  `customElementRegistry`): it runs in mount. If the check fails, mount throws `'unsupported'` before touching the DOM.
  The module itself must load without throwing on old engines, so registry creation is lazy, on the first mount, and
  wrapped.
- **Creating elements:**
  - Consumers use `root.innerHTML = '<td-button …>'` or `handle.create('td-button')`, which calls
    `document.createElement(tag, { customElementRegistry: registry })`.
  - `document.createElement('td-button')` (page registry) is documented as wrong. In development builds a
    MutationObserver on `root` warns once about an undefined `td-*` element.
- **Kit internals:** the three components create no nested custom elements (verified: no `createElement('td-…')` or
  `whenDefined` in their graph). `td-icon` is a helper, not an element. `td-hint` is only consumer-placed and is not in
  the suite.

**QĐ3. Root-aware core fixes** (no change in light DOM, where `getRootNode()` is the Document):
- **Focus:** new `src/utils/root.js` exports `activeIn(node)`, which returns
  `node.getRootNode().activeElement ?? null`. It replaces `ownerDocument.activeElement` at
  `td-form-element.js:806, 856`, `td-input-field.js:533, 669, 1099, 1169` and `field-affix.js:160, 163`, and the
  global `document.activeElement` at `td-input-field.js:606` (autofocus). Line `:1477` is checked, and changed only if
  it reads focus.
- **Press:** listeners stay at document level (`press.js:131`). The target is found with the first element in
  `e.composedPath()` that matches `PRESS_SELECTOR`, instead of `e.target.closest()`. This is also correct in light DOM,
  where the path starts at the target. Any `.closest()` or `contains()` used for pointer tracking (move, up) is made
  path-aware the same way.
- **Busy:** no change. `button-busy.js:54-66` already uses `composedPath()`, and the names stay `td-button`, so the
  `HOSTS` check at `:25` holds.
- **Submit:** `td-input-field.js:562` listens on `this.getRootNode()`, because `submit` is not composed. This only
  matters for password reveal, which is outside the embed suite. It is a correctness fix with a light-DOM regression
  check.
- **Events:** already `composed: true` (`td-base-element.js:277`). One regression assertion is added.

**QĐ4. Embed CSS build** (`scripts/build-embed.mjs`):
- **Explicit, reviewed file list**, not a closure engine: layers, tokens, theme-dark, icon, spinner, field, hint,
  button, loading, form-validation, alert, and the new `native-select.css`. The list is kept in
  `scripts/embed-manifest.json`.
- The files run through the same transforms as td.css. `build-css.mjs` exports its pipeline as a function, and the
  refactor is proven by td.css staying byte-identical.
- **Rewrites, in order:**
  1. `:root` becomes `.td-embed-root` in every selector (`tokens.css:16, 151, 367`, `field.css:16, 42`, the
     `:root[data-td-theme=…]` and `:root[data-td-glass=…]` compounds). Geometry and colour tokens then land on the
     wrapper.
  2. `Nrem` in declaration values becomes `calc(N * var(--td-embed-rem, 16px))`. `@media` and `@container`
     conditions are left alone, because their `rem` is the UA default and not the page's.
  3. **Custom-property quarantine** (`--td-embed-rem` is the only exemption: it is the embed's single inherited
     configuration property, so it is never quarantined): collect every `var(--name)` referenced in the output, including `--_td-*` and
     optional tints, that is never declared in it. Emit `--name: initial` for each one on `.td-embed-root`, before the
     token rules (lower in source order is not needed, because the token rules declare different names). Inherited
     CMS values then cannot reach the elements.
  4. A head block is prepended:
     - `:host { all: initial !important; display: block !important }`;
     - `.td-embed-root { font-family; font-size; line-height; color; direction: ltr; unicode-bidi: isolate;
       color-scheme }`, with values taken from the kit's existing base typography tokens.

     There is no `contain`. Position, inset, size and z-index go on a consumer-owned shell around the host
     (documented).
- **Static checks:**
  - no `:root`;
  - no `rem` outside conditions;
  - every `var()` resolves to a declaration or a quarantine entry;
  - every `animation-name` has its `@keyframes`;
  - every container query name has its `container-name`.
- **Bundle:**
  - The CSS text is inlined as a string constant.
  - The JS is built by esbuild 0.28.2 (already a devDependency) with `bundle: true`, `format: 'esm'`, minify, and the
    target from build-dist.
  - An `onResolve` plugin maps `td-icon.js`'s `./registry.js` to a generated subset holding `info`, `success`,
    `warning`, `error`, `close`, `eye`, `eye-off` and their aliases. Unknown names render nothing, as they do today,
    and `registerIcons()` can add more. Docs list the subset.
- **Version, without a self-referencing hash:**
  1. esbuild builds the bundle with the literal placeholder `"__TD_EMBED_BUILD__"`.
  2. `hash = sha256(cssText + jsWithPlaceholder).slice(0, 10)`.
  3. The placeholder is string-replaced by `` `${version}+${hash}` `` in the output.

  `check:embed` repeats exactly these steps and diffs the result. The value is for diagnostics only.
- **Artifact ownership:**
  - `dist/embed/` is owned only by `build-embed.mjs`.
  - `build-dist.mjs` skips `dist/embed/**` when it cleans files and when it checks for unexpected outputs, so it
    neither deletes nor flags them.
  - Freshness is checked by `check:embed`.
  - The package `build` / `prepublish` chain runs `build:css` → `build:dist` → `build:embed`, and `test:ci:static`
    runs `check:dist` and `check:embed`.

**QĐ5. `mountTdEmbed(host, opts)`** (`src/embed/mount.js`):
- **Options:** `{ theme: 'auto' | 'light' | 'dark' = 'auto' }`.
- **Checks:** everything is validated before `attachShadow`. A failure throws `TdEmbedError` with a `code` and leaves
  `host` untouched. The codes:
  - `'bad-host'`: not an HTMLElement.
  - `'unsupported'`: see QĐ2.
  - `'host-has-shadow'`: a shadow root that is not ours, tracked in a WeakMap.
  - `'already-mounted'`.
  - `'bad-theme'`.
- **Sheet:** `new view.CSSStyleSheet()` (page realm) + `replaceSync(text)`, built once per Document (a WeakMap keyed by
  `host.ownerDocument`). It is constructed before `attachShadow`, so a CSS failure also leaves the host untouched.
- **Mount steps:** `attachShadow({ mode: 'open', customElementRegistry: registry })`, or reuse our empty root from an
  earlier mount. Then set `adoptedStyleSheets = [sheet]` and append the root div.
- **`setTheme(mode)`:** validates the value (`TypeError` otherwise) and sets `data-td-theme`.
- **`unmount()`:** idempotent. It empties the shadow root (elements run their own `disconnectedCallback`), sets
  `adoptedStyleSheets = []` and marks the host unmounted. The second call is a no-op. Mounting again on the same host
  reuses the empty root, but only from the same module instance, which recognises its own root and immutable
  registry. A re-injected module instance gets `'host-has-shadow'` and must use a new host (documented).

**QĐ6. `native-select.css`.**
- The `select.td-dropdown__native` recipe moves to the new `src/styles/components/native-select.css`, which comes
  right after `field.css` in the manifest. The recipe spans `dropdown.css:79-145`, `:692-700` and `:730-753`: the
  host typography, the box, placeholder, hover, focus, disabled, coarse pointer and forced colours.
- Every extracted rule keeps its **original selector list verbatim**, including the unupgraded fallback
  `td-dropdown:not(:defined) > select` and the RTL / placeholder / hover / focus / disabled / coarse / forced-colors
  variants. A `select.td-native-select` branch with the same state is added as another item in the list.
- A regression check: a bare `<td-dropdown><select>` before definition is still styled (computed border and height,
  as before). The standalone class
  gets the typography that the `td-dropdown` host gives today.
- Dropdown markup and output do not change. A golden test for td.css confirms that the rendered dropdown is
  identical: the CSP baselines for `td-dropdown.*` stay green.
- New CSP state `td-native-select.standalone` with a baseline. The docs section goes in `docs/components/dropdown.md`.

**QĐ7. Docs.**
- **New `docs/guides/embed.md`,** linked from `docs/README.md` and the installation page. It covers:
  - when to use the embed;
  - the browser floor and the fallback;
  - Tampermonkey: the supported, tested metadata is the consumer's existing default sandbox (`@grant GM_*`, no
    `@sandbox` / `@inject-into`). "Page realm" in this plan means only the DOM constructors obtained through
    `host.ownerDocument.defaultView` (`CustomElementRegistry`, `CSSStyleSheet`). It is not a userscript world the
    consumer has to switch to;
  - bundling with esbuild;
  - mount, the handle, `create()` and the error codes;
  - the guaranteed suite and its attributes;
  - relabelling through `label`, never `textContent`;
  - `setTheme`, plus a sunrise/sunset snippet marked as consumer code;
  - `--td-embed-rem`;
  - the outer shell for positioning;
  - the icon subset.
- **The guide's limits section** states that:
  - isolation means CMS author-style isolation, not a security sandbox;
  - there is no association with a `<form>` or `<label for>` outside the shadow root;
  - there is no Trusted Types promise;
  - SSR, affixes, password reveal, toast, overlays and dropdown are not supported.
- ADR 0045 is rewritten for the registry pivot and marked "chấp nhận". `docs/internal/architecture.md` gets one
  paragraph on the root-aware core.

**QĐ8. Not doing (wave 2+).** td-dropdown (Popover + anchor: the ADR records only the requirement), toast, modal,
tooltip, other components, renamed `td-embed-*` tags, a closed root, and a fallback without a scoped registry.

## Tests

- **Node:**
  - QĐ1 gate: the built bundle defines nothing globally.
  - Static checks from QĐ4.
  - Token gate: every token in `test/embed/consumer-tokens.json`, plus every token the embed CSS uses, must have a
    declaration on `.td-embed-root` in light, and in dark wherever td.css has a dark value.
  - `check:embed` rebuilds and diffs, like `check:dist`.
  - Size budget for raw, min and gzip of `td-embed.js`. It is recorded after the first build with +10% headroom, and
    the delta versus the full `td.css` integration is reported in the CHANGELOG.
  - `activeIn` unit test.
  - Package isolation test: `exports['./embed']` resolves to `dist/embed/td-embed.js`. The artifact has no
    `import` / `export from` that points at `src/` or at another package file, because it is self-contained. Importing
    it and then the normal `src/form/td-button.js` in one realm still auto-defines `td-button` globally.
  - The `--td-embed-rem` exemption: the quarantine list does not contain it.
- **Browser, 3 engines** (`test/embed/td-v116-embed.engines.browser-test.js`). The test loads the BUILT bundle on a
  hostile page:
  - `html { font-size: 10px; direction: rtl; color-scheme: dark }`;
  - `* { font: 20px serif !important; color: red !important; box-sizing: content-box !important }`;
  - `button, input, select, textarea { all: revert !important; border: 3px solid lime !important }`;
  - `--td-accent`, `--td-space-md` and a private `--_td-btn-bg` set on `:root` and on the host;
  - a page-global `customElements.define('td-button', class extends HTMLElement {})`.

  The test cases:
  1. Mount succeeds, and the page's fake `td-button` does not interfere: our `td-button` inside `root` is the kit
     class.
  2. A reviewed set of properties is compared against a clean reference iframe (light DOM, full td.css, 16px root),
     in light and dark. The properties are padding, block size, font-size, line-height, border radius / width / color,
     background-color, color and gap, on `.td-btn`, the field box, input, textarea, alert and `td-native-select`.
  3. No leak outwards: a page `<button>` and a page `.td-btn` outside the host keep their page style.
  4. Focus: the root-aware path is exercised (focus input, then a structural re-render keeps focus). Programmatic
     `.value` set while focused keeps the caret.
  5. Press: pointerdown sets `[data-td-pressed]` and pointerup clears it.
  6. Busy: `run(async…)` blocks a second click.
  7. `label` relabel updates the text and the accessible name.
  8. `setTheme('dark' | 'light' | 'auto')`, with `'auto'` following `emulateMedia`.
  9. Two module instances (a query-string URL) both mount on separate hosts without conflict.
  10. Errors leave the host untouched: a host with a foreign shadow root, a bad theme, and a double mount.
  11. Unmount twice is fine, remount works, and after unmount the old elements are disconnected.
  12. `create('td-alert')` returns an upgraded kit alert.
  13. `td-*` events are observable from outside the host.
  15. `--td-embed-rem: 20px` set on the host changes the rem-derived geometry (for example the button block size
      scales), while the hostile `--_td-btn-bg` and `--td-accent` on the host stay blocked.
  14. Nested-parse probe (test only): a `td-probe-child` defined only in the scoped registry, set through `innerHTML`
      on a scoped parent, upgrades in all 3 engines.
- **CSP:** a small spec (or a matrix state) loads the embed bundle under the strict CSP and mounts with zero
  violations.
- **Gates:**
  - static: `check:css` (td.css changes only by the native-select move, and is otherwise identical), `check:dist`,
    `check:embed`, `test:node`;
  - browser: `test:csp` (all old baselines plus the new ones), `test:touch`, `test:responsive`, and the existing
    engines suites, especially press, dropdown and input-field;
  - CI.
