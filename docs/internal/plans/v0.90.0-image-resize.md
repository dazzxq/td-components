## Mục tiêu (tiêu chí nghiệm thu)

1. **Opt-in, kit không đặt số trần.** Không cấu hình thì hành vi y hệt v0.89 (không đọc file, không đổi file).
   - `td-dropzone`: property mới `imageResize` (object policy, mặc định `null`). KHÔNG kế thừa ngầm default của
     media picker.
   - `TdMediaPicker`: key `upload.imageResize` (qua `configureDefaults` hoặc option lúc mở, ưu tiên lúc mở), picker đưa
     policy đã chuẩn hoá xuống dropzone nội bộ của dialog upload.
2. **Policy** (chuẩn hoá + `Object.freeze`, chỉ chép key own đã biết; key lạ → bỏ qua + `console.warn` một lần; giá trị sai của key đã biết → `TypeError` đồng bộ, xem quy tắc chuẩn hoá bên dưới):

   | key | mặc định | ý nghĩa |
   |---|---|---|
   | `maxBytes` | `null` | trần byte đầu ra mỗi file (số byte nguyên; không nhận chuỗi "5MB" để tránh lệch MB/MiB) |
   | `maxPixels` | `null` | trần tổng điểm ảnh đầu ra |
   | `maxWidth` / `maxHeight` | `null` | trần cạnh đầu ra (theo hướng hiển thị, sau khi xoay EXIF) |
   | `quality` | `0.9` | quality JPEG lần encode đầu |
   | `minQuality` | `0.65` | sàn quality khi tìm để lọt `maxBytes` |
   | `maxEncodes` | `8` | tổng số lần encode tối đa một file |
   | `metadata` | `'keep'` | `keep` \| `keep-no-gps` \| `copyright` \| `none` |
   | `maxInputBytes` | `64 MiB` | chặn đầu vào (an toàn bộ nhớ, không phải trần site) |
   | `maxInputPixels` | `64e6` | chặn bom giải nén; 64 MP để lọt máy 61 MP (a7R IV/V) |
   | `maxInputSide` | `16384` | cạnh đầu vào tối đa (giới hạn canvas) |
   | `maxHeaderBytes` | `1 MiB` | phần đầu file được đọc để lấy kích thước/EXIF (JPEG: tới SOS) |
   | `processor` | `null` | hook thay engine: `(file, { policy, signal }) => File \| Blob \| null` |

   **Quy tắc chuẩn hoá (r1 #8)**: các trần là số hữu hạn > 0; `maxBytes`/`maxPixels`/`maxWidth`/`maxHeight`/
   `maxInput*`/`maxHeaderBytes`/`maxEncodes` phải là số nguyên (`maxEncodes` 1-32); `quality`, `minQuality` trong
   `(0, 1]` và `minQuality <= quality`; `metadata` thuộc 4 giá trị; `processor` là function hoặc null. Vi phạm bất kỳ →
   **TypeError ném đồng bộ** (setter `imageResize` của dropzone, `configureDefaults`, `openMediaPicker`), policy cũ giữ
   nguyên. Key lạ → bỏ qua + warn một lần. Chỉ đọc key own (không prototype).
   Policy không có trần đầu ra nào (`maxBytes`, `maxPixels`, `maxWidth`, `maxHeight` đều null) → vẫn hợp lệ: chỉ áp
   chế độ metadata (ví dụ `none` để xoá metadata không nén lại).
3. **Quyết định cho từng file** (theo thứ tự; nhận diện định dạng bằng magic bytes, không tin `file.type`/đuôi):
   - Đọc 64 byte đầu để sniff TRƯỚC (r2 #13). Không phải ảnh (PDF…) → policy không áp, chỉ kiểm `max-size` cũ trên file
     gốc rồi gửi nguyên. Các bước dưới chỉ áp cho ảnh nhận diện được.
   - File rỗng → `empty-file`. Vượt `maxInputBytes` → `input-too-large`.
   - JPEG/PNG: đọc header có giới hạn → kích thước thật (JPEG SOF0-3/5-7/9-11/13-15, PNG IHDR), Orientation EXIF (5-8
     đảo trục), APNG (`acTL` trước `IDAT`), PNG bit depth, JPEG đặc biệt (APP2 `MPF`, XMP chứa `hdrgm`, APP11 JUMBF/C2PA,
     dữ liệu sau EOI của ảnh chính). Không đọc được → `invalid-image` / `header-limit`. Vượt
     `maxInputPixels`/`maxInputSide` → `input-dimensions-too-large` (owner: panorama vượt trần = từ chối).
   - **Đã đạt mọi trần** (byte, pixel, cạnh):
     - `metadata: 'keep'` → gửi NGUYÊN file (cùng object File, không đọc lại).
     - chế độ khác, JPEG/PNG thường → **viết lại không mất dữ liệu** (giữ nguyên entropy JPEG / IDAT PNG, chỉ lọc
       segment/chunk metadata theo mục 5). JPEG/PNG đặc biệt (MPF, gain map, C2PA, đuôi, APNG) → `metadata-policy-unsupported`.
     - định dạng khác (GIF/WebP/AVIF/HEIC/SVG/BMP/…): `keep` → gửi nguyên; chế độ khác → `metadata-policy-unsupported`.
   - **Kích thước định dạng gửi nguyên (r1 #3)**: kit đọc kích thước GIF (logical screen) và WebP (VP8/VP8L/VP8X) để
     kiểm `maxPixels`/`maxWidth`/`maxHeight`/`maxInput*`. Định dạng raster khác (AVIF/HEIC/BMP/TIFF/…) chỉ được gửi
     nguyên khi KHÔNG có trần kích thước nào đang bật; có thì `format-not-transformable` (trừ khi `processor` trả file
     kit kiểm được). SVG không bị trần pixel (vector), chỉ trần byte.
   - **Vượt trần**:
     - JPEG thường → giải mã + resize + encode JPEG (mục 4), chèn metadata theo mục 5.
     - PNG thường 8-bit (không APNG) → giải mã + resize + encode PNG (giữ alpha, giữ PNG), metadata PNG theo luật PNG ở mục 5
       (outcome từng họ báo trong `optimization.metadata`).
     - JPEG đặc biệt, APNG, PNG 16-bit → `special-content-transform-required`.
     - Định dạng khác → `format-not-transformable`.
   - `processor` của site có → gọi nó thay engine ở nhánh "vượt trần" và nhánh "viết lại". Kết quả (r1 #4) phải CÙNG
     họ định dạng (magic bytes) với file gốc, đạt mọi trần đang bật (byte + kích thước kit đọc được; không đọc được mà
     có trần kích thước → không hợp lệ) và đạt chế độ metadata (kit đọc lại: `none`/`copyright` không còn EXIF GPS/XMP
     ngoài danh sách cho phép; `keep-no-gps` không còn GPS IFD/XMP) → sai thì `processor-invalid-result`; ném lỗi →
     `processor-failed`; `null` = dùng file gốc, chỉ hợp lệ khi file gốc đã đạt TOÀN BỘ policy (trần + metadata), không
     thì `processor-invalid-result`.
4. **Engine resize** (main thread, không Worker, không dependency):
   - Kích thước đích: `s = min(1, maxW/w, maxH/h, sqrt(maxPixels/(w*h)))` trên kích thước đã xoay, làm tròn xuống,
     mỗi cạnh ≥ 1.
   - `createImageBitmap(file, { imageOrientation: 'from-image', resizeWidth, resizeHeight, resizeQuality: 'high' })`
     (resize* theo hướng hiển thị). Option bị từ chối (TypeError) → gọi lại không resize, rồi thu nhỏ trên canvas bằng
     các bước ≤ 2× với `imageSmoothingQuality = 'high'`. Bitmap trả về sai kích thước đích → cũng thu nhỏ trên canvas.
     `createImageBitmap` lỗi → `decode-failed` (định dạng trình duyệt không giải được → `decode-unsupported`).
   - **Probe hướng xoay (r1 #7)**: lần đầu dùng engine, dựng JPEG 16×8 nửa trái đỏ / nửa phải xanh (canvas → toBlob),
     chèn EXIF Orientation 6, `createImageBitmap(..., { imageOrientation: 'from-image' })`, đọc pixel: phải ra 8×16 với
     nửa trên đỏ. Sai → mọi job cần giải mã JPEG có Orientation ≠ 1 trả `resize-unsupported` (không `<img>` fallback).
     Kết quả cache trong module. Probe thứ hai cho PNG `eXIf` (r2 #12): PNG 16×8 cùng mẫu, chèn `eXIf` Orientation 6,
     kiểm pixel như trên; sai → PNG có Orientation ≠ 1 cần giải mã trả `resize-unsupported`. Browser test cả 8 hướng (gồm lật gương 2/4/5/7) bằng pixel.
   - Canvas `document.createElement('canvas')` đúng kích thước đích, `getContext('2d')` null → `canvas-limit`.
   - `canvas.toBlob(type, q)`; blob null → `encode-failed`; `blob.type` khác MIME yêu cầu → `output-type-mismatch`.
   - JPEG: encode ở `quality`; quá `maxBytes` (đã cộng metadata sẽ chèn) → tìm nhị phân trong `[minQuality, quality]`;
     ở sàn vẫn quá → thu kích thước `× sqrt(budget/bytes) × 0.95` rồi lặp; tổng encode ≤ `maxEncodes`; giữ ứng viên
     NHỎ NHẤT đạt trần (không phải ứng viên cuối). Hết lượt → `cannot-satisfy-limits`.
   - PNG: encode một lần ở kích thước đích; quá `maxBytes` → thu kích thước như trên, ≤ `maxEncodes`.
   - Dọn dẹp ở mọi nhánh (`finally`): `bitmap.close()`, canvas `width = height = 0`.
   - Hủy: `AbortSignal` kiểm sau MỌI `await`; hủy → `aborted` (không hiện lỗi); kết quả về muộn bị bỏ.
   - Màu: canvas sRGB; ảnh P3 bị chuyển sang sRGB (ghi docs). ICC gốc không chép; ICC encoder tự sinh (nếu có) giữ.
5. **Metadata** (byte-level, KHÔNG parse XML, KHÔNG DOMParser → không đụng Trusted Types; mọi offset kiểm biên):
   - **JPEG nén lại**, thứ tự đầu ra: `SOI` → APP1 EXIF đã vá → APP1 XMP (nếu đủ điều kiện) → APP13 dựng lại (chỉ IPTC
     `8BIM 0x0404`) → toàn bộ segment + scan của encoder (bỏ SOI của encoder; giữ JFIF/ICC/APP14 encoder sinh).
   - **EXIF** (đúng 1 APP1 `Exif\0\0` hợp lệ; nhiều hơn 1 → bỏ họ EXIF): giữ nguyên bố cục TIFF (II/MM), vá tại chỗ:
     IFD0 Orientation (SHORT, count 1) → 1; Exif IFD PixelXDimension/PixelYDimension (SHORT hoặc LONG, count 1) → kích
     thước mới (SHORT mà giá trị > 65535 → để tag nguyên, báo `partial`); IFD0 ImageWidth/ImageLength (0x0100/0x0101)
     nếu có cũng vá (r1 #11); tag thiếu thì để thiếu. IFD0 có StripOffsets/TileOffsets (dữ liệu ảnh kiểu TIFF trong
     EXIF) → bỏ họ EXIF. X/YResolution, ResolutionUnit, CompressedBitsPerPixel giữ nguyên (thông tin, không ảnh hưởng
     giải mã; Canon/Nikon luôn ghi CompressedBitsPerPixel nên bỏ họ EXIF vì nó là quá tay). IFD1 (thumbnail):
     next-IFD của IFD0 → 0 và ghi 0 lên vùng IFD1 + dữ liệu thumbnail đã kiểm biên (không cắt APP1, MakerNote giữ đúng
     offset). Lỗi cấu trúc (offset ngoài biên, IFD vòng/chồng, số entry > 512, type lạ ở tag cần vá) → bỏ cả họ EXIF,
     báo `partial`, KHÔNG làm hỏng upload. APP1 sau vá luôn ≤ 65533 (không tăng kích thước).
   - **XMP** chỉ ở `keep`: chép NGUYÊN đúng 1 gói Standard XMP (`http://ns.adobe.com/xap/1.0/\0`) khi: decode UTF-8
     fatal được; không có APP1 Extended XMP và không chứa `HasExtendedXMP`; không chứa chuỗi nào trong danh sách chặn
     (Orientation, PixelXDimension, PixelYDimension, ImageWidth, ImageLength, XResolution, YResolution, ResolutionUnit,
     ColorSpace, ICCProfile, PhotometricInterpretation, BitsPerSample, SamplesPerPixel, YCbCrSubSampling,
     CompressedBitsPerPixel, NativeDigest, LegacyIPTCDigest, DocumentID, InstanceID, OriginalDocumentID, DerivedFrom,
     History, MetadataDate, ModifyDate, camera-raw-settings, crs:). Không đạt → bỏ XMP (`dropped`).
   - **IPTC**: đọc APP13 `Photoshop 3.0\0`, lấy resource `8BIM 0x0404` (IIM), kiểm từng dataset (tag 0x1C, độ dài
     chuẩn, không dùng extended length), dựng APP13 mới chỉ chứa 0x0404. Lỗi → bỏ IPTC, báo `partial`.
   - **Chế độ**:
     - `keep`: EXIF (gồm GPS) + XMP đủ điều kiện + IPTC.
     - `keep-no-gps`: EXIF với GPS IFD bị xoá tại chỗ (count → 0, ghi 0 lên entry + dữ liệu ngoài dòng đã kiểm biên;
       con trỏ 0x8825 giữ trỏ tới IFD rỗng), bỏ XMP, IPTC bỏ dataset địa điểm 2:90/2:92/2:95/2:100/2:101/2:26/2:27.
     - `copyright`: EXIF mới tối giản (IFD0: Orientation nếu ≠ 1 và chỉ khi KHÔNG nén lại, Artist 0x013B, Copyright
       0x8298) + IPTC chỉ 2:80 By-line và 2:116 Copyright Notice. Bỏ XMP.
     - Mọi chế độ trừ `keep`: COM và mọi APPn ngoài danh sách cho phép bị bỏ (r1 #6).
     - `none`: không EXIF/XMP/IPTC; riêng viết lại không mất dữ liệu mà ảnh có Orientation ≠ 1 → EXIF tối giản chỉ có
       Orientation (nếu không ảnh hiển thị sai hướng).
   - **Viết lại không mất dữ liệu (JPEG)**: duyệt marker từ SOI tới SOS, giữ thứ tự mọi segment không phải
     cấu trúc (danh sách cho phép bên dưới), thay/bỏ APP1/APP13 theo chế độ; byte từ SOS tới hết giữ nguyên.
     EXIF giữ Orientation gốc (pixel không đổi). Danh sách cho phép JPEG (ngoài `keep`): SOFn, DHT, DQT, DRI, DAC, DNL,
     APP0 `JFIF`/`JFXX`, APP2 `ICC_PROFILE`, APP14 `Adobe` + metadata chế độ cho phép; còn lại (COM, APPn khác) bỏ.
   - **PNG (r1 #5, #6)**: giữ PNG. Chunk cho phép mọi chế độ: IHDR, PLTE, IDAT, IEND, tRNS, gAMA, cHRM, sRGB, iCCP,
     sBIT, cICP, mDCV, cLLI, pHYs, bKGD. Chunk critical lạ (chữ đầu hoa) → `invalid-image`.
     - `keep`: `eXIf` vá như EXIF JPEG (Orientation → 1 khi nén lại, PixelX/Y); `iTXt` XMP theo cùng điều kiện XMP;
       `tEXt`/`zTXt`/`iTXt` khác giữ nguyên; `tIME` giữ; chunk ancillary lạ: giữ khi viết lại không mất dữ liệu, bỏ khi
       nén lại (không biết chúng có phụ thuộc pixel không).
     - `keep-no-gps`: `eXIf` xoá GPS tại chỗ; bỏ XMP; text chỉ giữ keyword Title, Author, Description, Copyright.
     - `copyright`: bỏ `eXIf`/XMP; text chỉ giữ Author, Copyright.
     - `none`: chỉ chunk cho phép.
     - Nén lại PNG: chèn chunk metadata giữ lại ngay sau IHDR (trước IDAT) của PNG encoder, CRC32 tính mới (bảng CRC
       trong module). Lỗi cấu trúc metadata → bỏ họ đó, báo `partial`.
   - Metadata chèn vào **tính trong `maxBytes`**: nếu riêng metadata ≥ trần hoặc không còn chỗ cho ảnh ở `minQuality`
     + kích thước nhỏ nhất → `metadata-too-large` (không lén bỏ metadata).
6. **Hàng đợi + trạng thái hàng** (td-dropzone):
   - Hàng đợi tối ưu dùng chung toàn module (FIFO, 1 file đang tối ưu tại một thời điểm, mọi dropzone/picker dùng chung).
   - **Bận / kết thúc lô (r1 #1)**: `dz.uploading` (và `busy()` của dialog upload) tính cả hàng `queued`/`optimizing`;
     dialog chỉ đóng tự động / toast khi MỌI hàng đã nhận ở trạng thái cuối (`done`/`error`). Đóng dialog lúc có hàng
     đang chờ/tối ưu → hỏi xác nhận như lúc đang upload; xác nhận thì hủy hết.
   - Trạng thái `data-status`: `queued` (chờ tối ưu) → `optimizing` → `uploading` → `done` | `error`. Hủy = gỡ hàng
     (nút × hiện có, không thêm nút). Không có policy → luồng cũ không đổi (`selected`/`uploading`/…).
   - Chữ trạng thái: `Đang chờ tối ưu…`, `Đang tối ưu ảnh…`; thanh tiến độ không xác định (tôn trọng reduced motion như
     hiện tại). Ảnh đổi xong: cột dung lượng hiện `30 MB → 4,2 MB`; live region nói `Đã giảm {name} từ 30 MB xuống
     4,2 MB` một lần.
   - Lỗi tối ưu → `error` với thông điệp gom nhóm: không đọc được ảnh / ảnh quá lớn để xử lý / định dạng này không tối
     ưu được / không giảm được xuống trần / tối ưu thất bại (bảng khoá label `optimizeError.<code>`).
   - **Thử lại**: hàng `error` do upload (không phải do tối ưu) có nút `Thử lại` (`td-dropzone__retry`, aria-label có
     tên file) khi có hook upload; thử lại dùng lại file đã tối ưu, KHÔNG tối ưu lại.
   - `files` / FormData / hook nhận **file đã tối ưu** (giữ tên file gốc; định dạng không bao giờ đổi trong v0.90).
     **Chỉ hàng tối ưu xong (hoặc gửi nguyên hợp lệ) mới vào `files`/FormData** (r1 #2). Còn hàng `queued`/`optimizing`
     → validity `customError` (`Đang tối ưu ảnh, vui lòng chờ`); còn hàng lỗi tối ưu → `customError` (`Có tệp không xử
     lý được, hãy gỡ ra`) tới khi người dùng gỡ hàng đó; xong thì cập nhật FormData. Test submit form không có hook.
   - `max-size` (và `upload.maxSize` của picker) khi có policy (r1 #9): `_add()` KHÔNG kiểm size đồng bộ nữa (vẫn kiểm
     `accept` và số lượng); mọi file vào hàng đợi, job sniff magic: ảnh kit xử lý (JPEG/PNG/GIF/WebP/SVG + gửi nguyên)
     dùng `max-size` làm trần ĐẦU RA (đầu ra > max-size → `cannot-satisfy-limits`) và `maxInputBytes` cho đầu vào; file
     khác → kiểm `max-size` trên file gốc, quá thì hàng `error` với thông điệp `rejectSize` cũ. `addFiles()` trả
     `accepted` gồm cả file sẽ bị lỗi trong job (ghi docs). Test MIME rỗng / MIME sai đuôi. Docs: `maxBytes ≤ max-size`.
   - **Snapshot trường upload (r1 #10)**: hook nhận thêm `originalFile` (File gốc đã nhận). Dialog upload chụp giá trị
     `uploadFields` lúc nhận file: `files-change` có thêm `detail.added` (r2 #10, additive: mảng File gốc vừa được nhận
     ở lần thêm này, phát đồng bộ TRƯỚC khi job nào chạy; `detail.files` giữ nghĩa cũ = file đã sẵn sàng); dialog chụp
     vào WeakMap theo File gốc, chỉ cho File chưa thấy và dùng
     đúng snapshot đó khi upload + khi thử lại. Test: đổi trường khi file thứ 2 đang chờ → file 2 dùng giá trị lúc nhận.
   - Hook upload nhận thêm `optimization` trong options thứ 2 (khi có policy):
     `{ changed, reasons: ('bytes'|'pixels'|'width'|'height'|'metadata')[], original: { name, type, size, width, height },
     output: { type, size, width, height }, metadata: { mode, exif, xmp, iptc: 'exact'|'patched'|'verbatim'|'rebuilt'|'dropped'|'absent'|'partial', gpsPresent: true|false|'unknown', contentCredentials: boolean } }`.
     Picker chuyển nguyên `optimization` vào `adapter.upload(file, { …, optimization })`.
7. **Docs**: `docs/components/dropzone.md` + `docs/components/media-picker.md` (policy, ví dụ Sony 33 MP → 12 MP/5 MB,
   cảnh báo GPS của `keep` NGAY cạnh option, hàng đợi, thử lại, `optimization`); hướng dẫn mới
   `docs/guides/image-upload-limits.md`: đồng bộ trần FE/BE (cùng đơn vị byte, BE ≥ FE, PHP `upload_max_filesize` /
   `post_max_size`, Symfony `File(maxSize)` + `Image(maxPixels)`, nginx `client_max_body_size`), server vẫn là ranh giới
   tin cậy (kiểm lại type/kích thước, tự strip nếu cần), nén lại đổi hash nên dedup exact-hash có thể lệch. ADR mới
   `0037-client-image-resize.md`.

## Quyết định đã chốt (không đổi khi làm)

- Không Worker, không OffscreenCanvas, không dependency, không fallback `<img>` (không đòi `img-src blob:`).
- Không tự đổi PNG → JPEG; không encode WebP/AVIF.
- JPEG đặc biệt / APNG / PNG 16-bit chỉ gửi nguyên.
- Metadata mặc định `keep` (owner, giống Cloudflare `keep`; docs ghi rõ mặc định của Cloudflare là `copyright`).
- URL upload (`uploadFromUrl`) không đi qua tối ưu.
- Không đụng crop step (chạy sau upload trên asset).
- Không thêm attribute mới (policy là property/option JS; không đổi PHP SSR).

## Rủi ro

- Safari/Firefox bỏ qua `resizeQuality` → chất lượng thu nhỏ kém hơn: đã có đường thu nhỏ từng bước ≤ 2× khi kích
  thước bitmap sai; khi đúng kích thước nhưng chất lượng thấp thì chấp nhận (ghi docs).
- Bộ nhớ: ảnh 64 MP giải mã ≈ 256 MB; hàng đợi 1 slot + trần đầu vào giảm rủi ro, không loại trừ trình duyệt bị kill
  trên máy yếu (server vẫn là ranh giới).
- Viết lại EXIF sai có thể làm file hỏng: mọi ghi đều tại chỗ, kiểm biên, và test đọc lại bằng `createImageBitmap` ở 3
  engine.
