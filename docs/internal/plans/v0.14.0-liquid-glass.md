# Plan — v0.14.0: real Liquid Glass + dwp tooltip + menu registry + hovercard

User decisions (2026-09-27): buttons become glass; floating surfaces as clear as iOS 26; toasts get per-type tinted
glass; tooltip = dwp look/behaviour in glass (a11y kept); checkbox round; add a menu option REGISTRY and a hovercard
that takes free-form HTML. Glass values settled in a Codex think-about debate (2 rounds, consensus; transcript notes in
docs/internal/design/liquid-glass.md §0). Branch `feat/v0.14.0-liquid-glass`.

## Decisions (normative)

**G1 — rules (rewrite docs/internal/design/liquid-glass.md R1):** glass = the functional control layer. Standalone buttons may be
Regular (`.glass`) or Prominent tinted (`.glassProminent`) — WWDC25 323, SwiftUI `GlassProminentButtonStyle`. Cards,
rows, tables, fields, checkboxes, page backgrounds: never. Controls inside an existing glass surface (modal, menu,
popover, toolbar group) use fills — no nested `backdrop-filter`. Grouped toolbar buttons share one glass parent.
"Frontmost glass wins": a menu/popover/hovercard over a glass modal stays glass, the covered modal dialog goes solid.

**G2 — material tokens** (starting values; light / dark): regular `rgb(255 255 255 / 40%)` / `rgb(12 14 18 / 44%)`;
strong `rgb(255 255 255 / 52%)` / `rgb(8 10 14 / 60%)`; fg `#111113` / `#f7f7f8`; blur `blur(16px) saturate(145%)
brightness(1.04)` (lg 20px) / `saturate(135%) brightness(0.92)`; 135° sheen gradient (24% → 7% → 0 → 8% white; dark
14/3/0/5%); rim: top edge 82% white, side edge 22%, bottom `rgb(0 0 0 / 8%)`; border 46% white; outer hairline
`0 0 0 1px rgb(0 0 0 / 8%)`; shadows `0 10px 30px -10px rgb(0 0 0 / 34%), 0 2px 8px -3px rgb(0 0 0 / 16%)` (lg deeper);
solid fallback `#f7f7f8` / `#17181c`; Clear 6% fill + dim 46% icons / 60% text. The recipe paints
`background-color` + `background-image: <status wash>, <sheen>`. Accessibility private-token fallbacks unchanged
(no backdrop-filter, `prefers-reduced-transparency`, `data-td-glass="off"`, `prefers-contrast`, `forced-colors`, reduced
motion); no `mix-blend-mode` vibrancy.

**G3 — buttons:** prominent variants = tinted glass: `color-mix(tint alpha)` + contrast film + sheen + rim + shadow +
blur; per-variant tokens `--td-btn-{variant}-tint/-alpha/-film/-fg` starting at 84% tint + 12% black film (primary
#2563eb, success #15803d, danger #b91c1c, info #1d4ed8) and warning = bright amber #f59e0b 86% + 10% white film +
`#111113` text. Secondary = strong neutral glass + 4% black film (dark: 0). Custom `color` attribute without a verified
pair → opaque fill (current behaviour). Dense contexts (`.td-table`, `[data-td-density="dense"]`, buttons inside a glass
surface) = glass look without `backdrop-filter`. Hover/active animate transform/glow only (never toggle the filter).
Disabled and loading use EXPLICIT state colours (no whole-element `opacity`, review ISSUE-1): disabled label keeps
≥ 4.7:1 on its own disabled fill (a muted but opaque-enough fill + dimmed text colour), loading spinner ≥ 3.2:1.

**G4 — toast:** own base `rgb(255 255 255 / 60%)` (dark `rgb(8 10 14 / 60%)`) + semantic wash 22% (success/info) /
26% (warning/error) painted above it; solid semantic icon kept (colour is not the only cue).

**G5 — contrast gate (acceptance, not constants):** token gate renders buttons (every variant, rest + disabled) and
toasts (every type) in light + dark over flat black, flat white, a checkerboard and a photo fixture, in Chromium,
Firefox, WebKit, for the states rest, disabled and loading (review ISSUE-1); samples interior background patches of the
same element rendered without text and takes the MINIMUM-contrast patch; the foreground is the EFFECTIVE composited
colour (computed colour with its alpha composited over that patch; the gate also asserts the element and its
ancestors have `opacity: 1`, so whole-element fading cannot hide a failure); requires ≥ 4.7:1 for labels, ≥ 3.2:1 for
icons/indicators (incl. the loading spinner). A failing pair is fixed by
tuning that variant's tokens, never the global recipe. Screenshots of the glass stories are reviewed by the lead.

**G6 — refraction:** not shipped (Safari 26 WebKit bug 245510, Firefox lacks SVG backdrop filters); roadmap backlog as an
experimental Chromium-only opt-in.

**G7 — checkbox:** round by default via `--td-checkbox-radius: 50%` (site override → square); check glyph unchanged;
no glass (content layer).

**G8 — tooltip (dwp port, glass):** dwp visuals and behaviour: arrow (a pseudo-element on the same element, same fill /
edge, no own backdrop-filter, positioned at the trigger centre via CSSOM `--td-tooltip-arrow-x/-y` even when the chip is
clamped), `--td-text-sm` (14px), `max-width: 18rem`, opacity-only fade 120ms, show on pointerenter for all pointer types
(touch included) and on any focus, hide on pointerleave / focusout / scroll / resize / Escape, fixed side with flip
when there is no room + viewport clamp. Kept td a11y: `role=tooltip`, `aria-describedby` while shown, D15 naming policy,
Escape via layers.js, hoverable with a short grace (WCAG 1.4.13). Attributes: keep `data-tooltip` /
`data-tooltip-position`; add aliases `data-tooltip-pos`, `data-dwp-tooltip`, `data-dwp-tooltip-pos` (dwp markup works
unchanged). Strong glass chip; custom `data-tooltip-color` stays a solid chip.

**G9 — menu option registry (TdMenu):** `TdMenu.define(name, items | (ctx) => items)` registers a named menu;
`TdMenu.register(name, item | item[], { order?, group? }) → unregister` lets other modules/sites ADD options to a named
menu without touching core (plugin hook); items may declare `when(ctx) → boolean` to show conditionally and `order`
(number) for placement; declarative triggers `data-td-menu="name"` (+ `data-td-menu-*` context data read into `ctx`)
are bound by `TdMenu.bindAll(root = document)` (event delegation, idempotent; no auto-run on import). `TdMenu.open(anchor,
name | items, opts)` accepts a registered name. Item model, keyboard, a11y and href whitelist unchanged.

**G10 — hovercard (new `TdHovercard`, port of dwp hovercard.js, glass):** rich popover on hover-intent (show 350 ms,
hide grace 250 ms) and keyboard focus; `role=dialog` non-modal, trigger `aria-haspopup="dialog"` + `aria-expanded` +
`aria-controls`; Escape closes and returns focus; stays open while pointer/focus is on the trigger or the card;
desktop-only binding (`(hover:hover) and (pointer:fine)`); strong glass (frontmost-glass rule), `placeFloating`, layer
`LAYERS.popover`. Content sources (free design, the user's requirement):
(a) `content(trigger) → Node | string | Promise<Node|string>` JS hook; (b) `<template id>` referenced by
`data-td-hovercard-template` (cloned — no parsing of strings); (c) `data-td-hovercard="url"` fetches a server fragment
**same-origin only** (dwp contract: JSON `{ html }` or text/html), cache per URL, render-token guard for stale
responses. **String HTML is a TRUSTED hatch** (developer / same-origin server-escaped fragments only; never raw user
input) — documented in security.md; CSP note: markup with `style=""` is blocked under strict CSP, use classes.
Loading + error states (Vietnamese labels).
**Public API (review ISSUE-3):** `TdHovercard.bind(trigger, { content?, template?, url?, label? }) → unbind` (one of the
three sources; binding sets the trigger ARIA); `TdHovercard.bindAll(root = document) → unbind` binds declarative
triggers (`data-td-hovercard="url"`, `data-td-hovercard-template="id"`) by event delegation on `root` — idempotent, no
auto-run on import; `TdHovercard.close()`; `TdHovercard.labels` (Vietnamese). Teardown removes listeners, ARIA it added,
and closes the card.
**Stale results (review round 2 ISSUE-7):** ONE render token governs every asynchronous source — `content()` Promises
and URL fetches alike; it is bumped on open, trigger switch, close and unbind, and a resolution OR rejection carrying an
old token never touches the card (no content swap, no error state, no reopen). Tests: A resolves after B (B wins);
a Promise resolving and another rejecting after close (card stays closed, unchanged).
**Keyboard (review ISSUE-2):** focus on the trigger (keyboard) opens the card after load. The card registers with
layers.js at `LAYERS.popover` as a keyboard boundary: Tab on the trigger → first focusable in the card (`handled`), or
`pass` when the card has none; Shift+Tab from the first card focusable → back to the trigger; Tab from the last card
focusable → close the card, move focus to the trigger and return `pass` so the native order (or a modal's trap)
continues after the trigger; Escape closes and returns focus to the trigger. Tests with interactive card content on a
normal page AND from inside an open TdModal.
**Accessible name (review ISSUE-5):** card `aria-label` = `label` option → trigger `data-td-hovercard-label` → trigger
`aria-label` → trigger text (trimmed, capped) → `TdHovercard.labels.dialog`; tests for an explicit label and the
text fallback.
**Stylesheet (review ISSUE-4):** `src/styles/components/hovercard.css` added to `src/styles/manifest.json` (before
`utilities.css`), `td.css` rebuilt and committed; `.td-hovercard` added to the td-css block test.
