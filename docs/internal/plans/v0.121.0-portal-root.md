# v0.121.0: `portal="local"` / `portalRoot` (popup in the host's shadow root)

Requested by afamily-prj (new consumer, 23/11, owner-approved as relayed): a userscript that renders its UI inside a
CLOSED shadow root on a third-party CMS page. td-dropdown always portals its menu to `document.body`
(src/form/td-dropdown.js:1101), so the page's own scripts can reach it: fake `input` into the search box (fires the
app's authenticated search), `.click()` an option even while hidden, rewrite labels / `data-nav`. Additive, opt-in;
without the new attribute / property everything is byte-identical.

## Decisions (QĐ)

### QĐ1 Shared helper, generic API
- New `src/utils/portal.js`: `resolvePortalRoot(host)` returns, in order:
  1. `host.portalRoot` when it is a connected `Element` or `ShadowRoot` (property wins). These are the only Nodes that
     can hold a rendered element; any other value (Text, Document, a DocumentFragment, a disconnected node) is
     ignored with one `warnOnce` and resolution continues with step 2 (review R1: explicit contract);
  2. `host.getRootNode()` when `host.getAttribute('portal') === 'local'` and that root is a `ShadowRoot`;
  3. `document.body` (today).
  Other values of `portal` (and `portal="local"` outside any shadow root) ⇒ `document.body`.
- The helper is generic: every body-portalling popup can adopt it with the same attribute / property names. This
  release adopts it in **td-dropdown only** (the request's minimum). Other popups (tree-select :600, chip-input :582,
  datetime-picker :1168, color-picker :256, icon-picker :379, td-menu, tooltip, hovercard, td-modal :283) adopt it
  later on request; the docs say so.

### QĐ2 td-dropdown adoption
- Attribute `portal` (observed) + property `portalRoot` (getter/setter, in UPGRADE_PROPS and in the preupgrade-props
  case table `src/base/td-v0541-preupgrade-props.engines.browser-test.js`).
- `afterRender` appends the menu to `resolvePortalRoot(this)` instead of `document.body`.
- Changing `portal` / `portalRoot` while connected: close if open, then move the existing menu node to the new root
  (same node, listeners kept). Disconnect removes the menu as today (:1105); reconnect recreates it in the root
  resolved at that time.

### QĐ3 Outside click, focus, keyboard inside a (closed) shadow root
- Today `_boundPointerOutside` (:368) is a capture listener on `document` testing `e.target`. In a shadow root the
  target seen at `document` is retargeted to the shadow host, and for a CLOSED root `composedPath()` seen from
  `document` does not include the inner nodes. Capture reaches `document` BEFORE the ShadowRoot, so the decision
  must not rely on a marker set by the root listener (review R1). Order-safe split, with a local root `R`:
  - the `document` capture listener skips any event whose path contains `R.host` (for a closed root the host is
    still in the path seen from `document`); events elsewhere in the page close as today;
  - a capture `pointerdown` listener on `R` classifies events that reach the root: inside the dropdown host or the
    menu ⇒ keep open, anything else in `R` ⇒ close; either way it records the event in a WeakSet ("seen by R");
  - a BUBBLE `pointerdown` listener on `document` (runs after every listener inside `R`, review R2) handles the rest:
    an event whose path contains `R.host` but that `R` never saw (a press on the host's own box, outside any child of
    the root) ⇒ close. If the app stops propagation inside its root the bubble listener does not run; that only
    affects such host-box presses (documented).
  When `portalRoot` is an Element in the light DOM (not a ShadowRoot) the document listener works as today. Tests use
  real `pointerdown` (not only `click`). With the body portal the code path is unchanged.
- Focus checks that use `document.activeElement` in the dropdown (focus-out close, Tab handling, focus return) must
  use the active element of the relevant root (`root.activeElement` for a ShadowRoot) — list every such site in the
  implementation and cover it with a test.
- Esc / Tab go through the layers registry (`registerLayer`, src/utils/layers.js); it already uses
  `composedContains` (:116) — verify with a closed-root test, fix only if the test fails.

### QĐ4 Positioning
- The menu stays `position: fixed` with viewport coordinates (`_placeMenu`). A ShadowRoot is not an element, so the
  menu's containing block is determined by the shadow host's ancestors: if the host or any ancestor of it has
  transform / filter / perspective / contain: paint|layout / will-change: transform, `fixed` is relative to that
  ancestor. With a local root `_placeMenu` measures the containing block once per placement (review R1: scale
  included, e.g. td-modal's `scale(0.95)` open animation): write `left: 0; top: 0` (CSSOM), read the menu's
  `getBoundingClientRect()` (origin `ox, oy`) and the scale factors `sx = rect.width / menu.offsetWidth`,
  `sy = rect.height / menu.offsetHeight` (1 when 0). Then CSS `left = (x - ox) / sx`, `top = (y - oy) / sy`, and the
  sizes written in CSS px (width, scroller max-height) are divided by `sx` / `sy`, so the on-screen box matches the
  body-portal result. Rotation / skew are out of scope (documented). Body portal: unchanged (no extra measure).
- `portalRoot` pointing at a node inside a transformed ancestor (e.g. a td-modal dialog with its open animation) is
  covered by the same compensation.

### QĐ5 Theme, z-index, CSS
- Theme: `bridgeTheme(menu, this)` (layers.js:652) is kept; inside the same root the menu also inherits tokens from
  the host. Test light + dark (`data-td-theme` on an ancestor of the host and on an element inside the root).
- z-index: the menu keeps the popover layer token. Inside the root it stacks above content of that root (a td-modal
  rendered INSIDE the same root). Known limit, documented: td-modal and other overlays still portal to body, so a menu
  in a shadow root cannot stack above an overlay that lives in body; the consumer's modal must live in the same root
  (or wait for td-modal to adopt QĐ1).
- CSS: the kit inserts no stylesheet; with a local root the app loads td.css inside the shadow root (documented).
- inert: inert-lock only touches `document.body` children; a floating menu in a shadow root is never inerted by it.
  A body-level blocking overlay making the host inert also makes the menu inert: expected (documented).

### QĐ6 `trusted-only`: not added
(Revised after the R1 security review.) A closed shadow root is DOM encapsulation, not a security boundary: when the
page's scripts share the userscript's JS realm, the page can wrap `Element.prototype.attachShadow` before the userscript
runs (and keep the "closed" root) or patch the kit's prototypes. In that same realm an `isTrusted` filter inside the kit
is not a boundary either (the page can patch the kit itself); in an isolated world (extension content script, a
userscript-manager sandbox such as a `@grant` other than `none`) the page cannot reach the nodes, so the filter is
unnecessary. It would also break programmatic use and the kit's own tests. So `trusted-only` is still not added; the docs
describe `portal="local"` as DOM encapsulation and point consumers that need isolation to an isolated world. The
consumer can filter in its own listeners if it wants. Told to the requester.

## Tests
- node: `resolvePortalRoot` cases (property wins, disconnected property ignored, local + shadow, local + document,
  other values).
- engines (new `src/form/td-v121-dropdown-portal-root.engines.browser-test.js`), open AND closed shadow roots:
  1. `portal="local"`: the menu is a child of the shadow root, `document.body` has no `.td-dropdown__menu`;
  2. select by click, search (type in the box), keyboard (arrows, Enter, Esc, Tab), all work;
  3. click inside the menu does not close; click elsewhere inside the root and in the page closes;
  4. `portalRoot` property wins over the attribute; changing it while open closes and moves the menu;
  5. reconnect (move the host) recreates the menu in the new root;
  6. theme light/dark in the root;
  7. positioning: host inside an ancestor with `transform` (and a td-modal-like transformed dialog inside the root):
     the menu's rect sits under the trigger (±1 px);
  8. no attribute: menu in body, as today;
  9. stacking: a td-modal-like dialog rendered inside the same root overlapping the open menu:
     `root.elementFromPoint()` at a point inside both returns a node of the menu;
  10. positioning under `scale(0.95)` on an ancestor of the host: the menu's rect matches the trigger (±1 px);
  12. a real pointerdown on an exposed area of the shadow host itself (padding) closes the menu;
  11. invalid `portalRoot` (Text node, disconnected element): one warning, falls back to the attribute / body.
- Regression: existing dropdown suites, preupgrade table, test:csp, test:node, full WTR engines group in CI.
