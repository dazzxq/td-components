# v0.99.0: per-tab disabled state on `<td-tabs>` (dsuite request 07/11)

## Goal

On dsuite's product CREATE page, every edit-page tab is shown. Tabs that need a saved product ("Giá và biến thể",
"Liên quan và kênh bán", SEO, module panels) stay visible but locked. Backward compatible: nothing changes for tabs
without `disabled`.

## Contract

Data (`tabs` property):
- `disabled?: boolean`. Only `=== true` locks a tab. Any other value means enabled, so `'false'` or `1` cannot lock it
  by accident.
- `disabledReason?: string`. Trimmed, at most 200 characters (the rest is cut). Rendered as TEXT, never HTML. Used only
  when `disabled` is true.

Markup (link mode, server `<a href>` children): `<a href="…" aria-disabled="true">` or `<a href="…" data-disabled>`
marks the tab disabled. `data-disabled-reason="…"` gives the reason. There is no other markup tab source (tablist tabs
are data only).

Rendering:
- Tablist tab (`<button role="tab">`): `aria-disabled="true"`, never the native `disabled` attribute, so it stays
  focusable and arrow keys reach it (WAI-ARIA tabs pattern). It is also not `aria-selected="true"`.
- With a reason: `title` = reason (native tooltip on hover), plus the `tab-blocked` event on every blocked activation
  for the host's own toast or hint. The kit adds no tooltip component or toast. Docs say so.
- Link-mode tab: `<a class="td-tabs__tab" aria-disabled="true">` with NO `href` (not navigable, no context-menu "open
  in new tab"), `tabindex="0"` so it stays a Tab stop like the other links, and `role="link"` (an `<a>` without href
  has no implicit role).
- Visual: muted using the existing `--td-btn-disabled-fg` token (light and dark already defined),
  `cursor: not-allowed`. No hover or pressed look: the line 338 rule already excludes `[aria-disabled="true"]`. The
  same exclusion goes on the hover rule AND on the forced-colors pressed rule. The icon inherits the muted colour.
  Count pill: its own fg/bg custom properties do not inherit, so on a disabled tab the pill uses the neutral tone with
  `--td-btn-disabled-fg` text, ignoring `tone`. Forced colors: label, icon and pill in `GrayText`, no pressed look.
  Contrast: the repo's contrast gate measures disabled controls at its 2.2:1 disabled floor (they are not skipped).
  Add the disabled tab label and its count pill, light and dark, at that threshold.

Behaviour:
- Click, Enter or Space on a disabled tab does nothing: no selection, no panel shown, no `tab-change`, no
  `onChange`. Instead it fires `tab-blocked`: bubbles, composed, NOT cancelable, detail `{ tabId, reason }`, where
  `reason` is `''` when none is set. `tabId` matches the existing `tab-change` detail; tell dsuite they asked for `id`.
  In link mode the click is also `preventDefault()`-ed, and `tab-click` is not fired for a disabled tab.
- Arrow keys, Home and End move focus onto disabled tabs as usual. `activation="auto"`: landing on a disabled tab
  focuses it only. It does not select and does not fire `tab-blocked` (that event is for an explicit activation).
- `active-tab`, `setActiveTab(id)` or `select(id)` (whatever the public API is) with a disabled id is ignored: the
  current tab stays. With no valid current tab (first render, or the current tab was removed), the fallback is the
  first ENABLED tab. All disabled → nothing selected, no panel shown.
- Runtime toggle (`tabs` re-assigned with a different `disabled` state): re-renders. If the active tab becomes
  disabled, the active tab moves silently to the first enabled tab (no `tab-change`, the same as the existing
  "active tab removed" path). Enabling a tab changes nothing else.
- Link mode URL matching (pathname and `match-hash`): a disabled tab is never the current tab. On a re-match
  (`popstate`, `hashchange`, `update()`) whose match is disabled, the previous current tab stays current if it is
  still enabled (the "fall back to the current tab" rule). On the FIRST resolve with a disabled match there is no
  current tab: link mode keeps its v0.83.0 rule of never marking `aria-current="page"` on a link for a page the user is
  not on. Tablist mode does fall back to the first enabled tab. An explicit `active-tab` naming a disabled tab is
  ignored in the same way.
- Overflow (horizontal scroll) mode and `layout`: no change. A disabled tab is measured like any other.

## Tests (3 engines, `src/display/td-v099-tabs-disabled.engines.browser-test.js`, real keys via sendKeys)

1. a11y attrs: `aria-disabled="true"`, not `disabled`, `title` = reason, not selected. Link mode: no href,
   `role="link"`, `tabindex="0"`.
2. Click: no change, no `tab-change`, `tab-blocked` once with `{ tabId, reason }`, not cancelable.
3. Keyboard manual: arrows reach the disabled tab (focus); Enter and Space are no-op plus `tab-blocked`. Auto
   activation: an arrow onto it does not select and fires no event.
4. `active-tab`, `setActiveTab` or `select` to a disabled id → ignored. First render with `active-tab` disabled → first
   enabled tab. All disabled → none.
5. Runtime toggle: the active tab is disabled → falls back silently; re-enable → selectable.
6. Link mode: a disabled link click is prevented, no `tab-click`, `tab-blocked` fired; `match-hash` / pathname never
   make it current. Server markup `<a aria-disabled="true">`, `data-disabled` and `data-disabled-reason` work.
7. With `icon`, `count`, and overflow mode: renders and is measured. The computed colour of the label, the icon and
   the count pill text is the disabled colour. The pill ignores `tone` (neutral background).
8. Light and dark: the computed colours are the disabled token in each theme. Forced colors (emulated where the engine
   allows it): `GrayText`, no pressed look.
9. Link-mode re-match: current A (enabled), then the hash changes to disabled B → A stays current. First load on a
   disabled match → no current tab.

Node test and SSR: none, because no PHP helper exists for tabs. CSP matrix: add a state `td-tabs.disabled` and
capture its baseline. Contrast gate: the disabled tab label and pill at the 2.2:1 disabled floor, light and dark.

## Part 2: scroll-lock gutter under a host `scrollbar-gutter: stable` (dsuite bug report 07/11)

Problem (verified by dsuite on 0.98.0, Chromium with classic scrollbars): when the host page sets
`html { scrollbar-gutter: stable }` and the page does NOT overflow, `innerWidth - root.clientWidth` is 0 (CSSOM
`clientWidth` subtracts only a scrollbar that is drawn), yet layout and fixed overlays are 15px narrower. So:
- `lockScroll()` (`src/utils/scroll-lock.js` ~211) reads `_gap = 0` → the gutter colour lease never paints → a light
  15px strip beside the dark scrim.
- `hideKeepingGutter()` (~162) reads `width = 0` → plain `overflow: hidden` (harmless here, the host gutter stays).
- On a TALL page with the host gutter, the "held" check `root.clientWidth <= before` compares 785 (scrollbar drawn)
  with 800 (gutter now empty, not subtracted) → wrongly decides the gutter did not hold → falls back to padding →
  double gutter (dsuite's 02/11 workaround).

Fix: one helper `stripWidth(root)` = the strip a fixed overlay leaves uncovered:
`max(innerWidth - root.clientWidth, round(innerWidth - probe.getBoundingClientRect().width))`, where `probe` is a
temporary `div` styled through CSSOM `setProperty` only (position fixed, inset 0, visibility hidden, pointer-events
none: CSSOM-only style writes, which the kit's CSP policy permits; no markup `style="…"`, no `<style>`), appended to `document.body || root` and removed at once; any throw → the old
formula. Used for:
1. `_gap` in `lockScroll()` (read before anything changes, as today);
2. `width` (before) in `hideKeepingGutter()`;
3. the held check: after `scrollbar-gutter: stable` + `overflow: hidden`, the gutter held iff `stripWidth(root) >=
   width` (strip still there) instead of comparing `clientWidth`. The `::-webkit-scrollbar` case (Chromium ignores
   the gutter on a custom root scrollbar) still yields strip 0 → padding fallback as today.
No change when there is no host gutter and no scrollbar (probe width = innerWidth → 0, nothing reserved), nor on
overlay-scrollbar engines (0 everywhere). Cost: one forced layout per first lock / per release check, same as today's
`clientWidth` reads.

Tests: `src/utils/td-v099-scroll-lock-host-gutter.engines.browser-test.js` (3 engines; each case asserts its
precondition "a host `scrollbar-gutter: stable` leaves a strip > 0" and skips with a note when the engine has overlay
scrollbars, as local macOS headless does; CI Linux has classic bars):
- short page + host gutter: open a `td-modal` → `<html>` gets the inline gutter colour (scrim over canvas, the existing
  `expected()` helper from scroll-lock.gutter.engines.browser-test.js), strip width unchanged, no padding-inline-end
  added; release → inline background and styles restored.
- tall page + host gutter: lock → no padding fallback (no inline `padding-inline-end`), strip width unchanged, content
  does not move; release restores.
- existing scroll-lock suites (gutter, scrollbar, modal viewport) stay green: no host gutter = old behaviour.
Docs: CHANGELOG fix line; `docs/` page that describes the gutter colour (find where holdGutterColor is documented) gets
one sentence: a host `scrollbar-gutter: stable` is supported, short or tall page.
