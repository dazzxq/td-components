# v0.115.0: `<td-input-field type="password" revealable>`

Owner request: dsuite-19 on 15/11, for its owner; dcms2-1a will use it too. Login, OTP and 2FA pages in dsuite and dcms2 must
look the same: an eye button at the end of a password field shows or hides what the user typed.

## Goal

- `revealable` is a boolean attribute (and a `revealable` property) on `<td-input-field>`. It only does something when
  `type="password"`. For any other type it is ignored.
- An eye button sits at the end of the field. A press switches the inner `<input>` between `type="password"` and
  `type="text"`.
- Button accessible name: "Hiện mật khẩu" while hidden, "Ẩn mật khẩu" while shown. `aria-pressed` follows the state and
  `aria-controls` points at the input.
- Icon: `eye` while hidden (the action), `eye-off` while shown. Both icons already exist in `src/icons/icons.json`.
- Focus stays where it was. With a pointer, pressing the button does not move focus away from the input, and the caret
  position is kept. With the keyboard, the button is a normal Tab stop (WCAG 2.1.1: reveal has no keyboard equivalent
  on the input, unlike the number stepper whose `tabindex="-1"` is backed by arrow keys). Enter or Space toggles and
  focus stays on the button, so the user can press again; Shift+Tab goes back to the input. The request's "focus stays
  in the field" is met for pointer and touch, where it matters (keyboard users stay where they pressed).
- `autocomplete`, `name` and the form value are untouched. Password managers keep working.
- The field goes back to hidden (`type="password"`) on its form's `submit` event (submit button, Enter,
  `requestSubmit()`), on form reset, on `pagehide`, and when the element is disconnected. For those event-driven
  submissions the browser sees a password field when it offers to save credentials. `HTMLFormElement.submit()` and AJAX
  sends fire no `submit` event and are not covered: the consumer calls `field.conceal()` first (documented, QĐ4).
- Default: without `revealable`, render, markup and behaviour are byte-for-byte unchanged.

## Decisions (QĐ)

**QĐ1. State.** A private `_revealed` boolean and a public read-only `revealed` getter. Add `reveal()`, `conceal()` and
`toggleReveal()` methods; they do nothing when `revealable` is off, the type is not password, or the field is disabled. Each
state change dispatches `td-reveal` with `detail: { revealed }` (bubbles, not cancelable). No attribute reflects the state:
it is session-only and must not end up in SSR or in a saved DOM.

**QĐ1b. Eligibility.** The effective state is `_revealed && revealable && type === 'password' && !disabled`. When
`revealable` is removed or `type` changes away from password, the state is cleared (`_revealed = false`, one `td-reveal`
event if it was true). Coming back to password + revealable starts hidden.

**QĐ2. Rendering.** When `revealable` and the type is password, `_affixState()` returns a box even if there is no
prefix/suffix (new flag `reveal: true`). `render()` puts `<button type="button" class="td-field__reveal" …>` as the last
element in the box, after the suffix and before the hidden unit span. Its icon is a `data-td-icon` slot that
`fillIconSlots` fills. The current affix-only selector does not reach it, so `afterRender` and every toggle call
`fillIconSlots(button, '[data-td-icon]')` on the button itself (`eye` / `eye-off` written to `data-td-icon` first). `render()` writes `type="password"` when hidden and `type="text"` when
revealed, so a structural re-render (label, size, affix…) keeps the current state. `revealable` joins `_structural`
(adding or removing it re-renders) and `observedAttributes`/`booleanAttributes`.

**QĐ3. Toggling without a re-render.** Toggle writes only `control.type`, `aria-pressed`, `aria-label` and the icon slot
(re-filled). Before writing `type` it saves `selectionStart/End` while the input is focused, and restores them after.
`mousedown` on the button calls `preventDefault()` so pointer focus stays in the input. `_bindAffix` already skips
interactive slot targets; extend that check to `.td-field__reveal`. `pointerdown` gets `touch-action: manipulation` in
CSS (no double-tap zoom).

**QĐ4. Auto-hide.**
- `submit`: a capture listener on `this.ownerDocument` while connected. When `event.target === this.form`, it calls
  `conceal()`. `submit` fires before the browser reads the form and before the navigation, so the form's
  credential-save prompt sees a password field.
- `formResetCallback` → `conceal()`.
- `disconnectedCallback` → `conceal()` and remove the listener.
- `pagehide` → `conceal()`, so a shown password is not restored from bfcache.
- `HTMLFormElement.submit()` fires no `submit` event and is NOT covered. A `formdata` listener is rejected: kit
  `form-dirty.js:143` builds `new FormData(form)` on every input, which would conceal on every keystroke. Docs say:
  submit through a submit button or `form.requestSubmit()`, or call `field.conceal()` before `form.submit()` / an AJAX
  send. dsuite and dcms2 login forms submit with a button (to confirm with each when releasing).

**QĐ4b. Sync after render / SSR adoption.** After every render and after SSR adoption, a silent `_syncReveal()` (no
event) writes `aria-label` (from messages, so overrides apply to SSR markup too), `aria-pressed`, `aria-controls`,
`disabled` and the icon.

**QĐ5. Disabled / readonly.** When the field is disabled (attribute or ancestor fieldset), the button is disabled and the
field conceals. `_applyInteractivity` sets this. Readonly still allows revealing, because the user may want to read a
generated password.

**QĐ6. Labels.** Add `reveal: 'Hiện mật khẩu'` and `conceal: 'Ẩn mật khẩu'` to `TdInputField.messages`, read through
`_msg`, so a site can override them the usual way. The button carries no visible text.

**QĐ7. CSS** (`src/styles/components/field.css`, Minimal surfaces + touch standard):
- `.td-field__reveal` is a borderless, transparent square inside the box, `color: var(--td-text-muted)`, with an icon of
  the same size as affix icons. It stretches to the box height. On coarse pointers the hit area is
  `max(…, var(--td-touch-min))` on the inline axis.
- Decorative hover goes inside the hover gate. Pressed feedback uses `:is(:active,[data-td-pressed])` outside the gate
  (`check:css` rule 4). `:focus-visible` uses the kit's focus ring. The disabled state uses the disabled tokens.
- Logical properties only (`margin-inline-end` …).
- No `style=""`. CSP-strict as usual.

**QĐ8. SSR.**
- `_ssrBoxOk` / the skeleton check (`td-input-field.js:1016`) accept a trailing `button.td-field__reveal` only when
  `revealable` and the type is password. Its attributes are compared with `render()`'s, ignoring `aria-label`, which
  comes from messages.
- PHP `td_field(…, ['revealable' => true])` in element mode prints `revealable` on the host
  (`php/td.php:6220-6228`) and the button inside the box via `td__affix_box`.
- Native mode (no custom element, no JS) ignores `revealable`: the button would do nothing without JS. This is
  documented.

**QĐ9. Not doing.**
- No "hold to reveal".
- No auto-hide timer.
- No reveal on `contenteditable` or textarea.
- No change to `td-password-meter`. It reads `host.value`, so it does not care about the type.

## Tests

- **Node** (`src/form/td-input-field*.test.js` DOM shim):
  - With the default (no `revealable`), render output is identical. Snapshot the string for password and text.
  - `revealable` + password renders the box with the button, the correct `aria-pressed`/`aria-label`/`aria-controls`, and
    `type="password"`.
  - `revealable` on `type="text"` renders nothing extra.
  - A structural re-render keeps the revealed state.
- **Browser, engines** (Chromium/Firefox/WebKit), new `td-v115-password-reveal.engines.browser-test.js`:
  1. Click toggles type, aria and icon. The input keeps focus, and the caret position is kept after typing.
  2. Keyboard: Tab reaches the button, Space toggles, focus stays on the button; Shift+Tab returns to the input.
  2b. The icon slot holds the `eye` SVG when hidden and `eye-off` when shown (after bind and after each toggle).
  2c. Eligibility: revealed → remove `revealable` → type password, no button; add it back → hidden. Revealed →
      `type="text"` → `type="password"` → hidden.
  3. Submit of the owning form conceals before the submit handler sees the form. Use a `submit` listener on the form
     that asserts `input.type === 'password'`, with `preventDefault` so the page does not navigate.
  4. `form.reset()` conceals. `remove()` conceals.
  5. Disabled: the button is disabled and `reveal()` does nothing. An ancestor fieldset that is disabled does the same.
     Readonly can reveal.
  6. `autocomplete="current-password"` survives toggling. The FormData value is unchanged.
  7. `td-reveal` event fires once per change.
  8. SSR (PHP-shaped markup with the button) is adopted without a re-render (`_ssrFreshRender` false), and with an
     overridden `messages.reveal` the adopted button gets the override as its `aria-label`.
  9. `form-dirty` attached to the form: typing while revealed does not conceal.
- **Gates:** `check:css`, `npm run test:csp` (new states), golden tokens if a token is added (none planned), touch
  spec (`test/touch/touch.spec.mjs`): a tap on the reveal button does not focus the input on coarse pointers, and the
  hit area is ≥ 44 px.
