### Key Insights

- The proposed JPEG splice is directionally sound only for one validated EXIF APP1. Blindly copying XMP or the whole Photoshop APP13 also copies stale dimensions/orientation, thumbnails, ICC resources, and other unrelated data. APP13 must be rebuilt from IPTC resource `0x0404`, not copied wholesale. — Source: [Adobe Photoshop file-format specification](https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/)
- TIFF/EXIF can be safely modified without moving MakerNote data: validate `II`/`MM`, retain the complete TIFF byte layout, patch fixed-size values in place, and keep every offset relative to the TIFF header unchanged. — Source: [TIFF 6.0](https://www.itu.int/itudoc/itu-t/com16/tiff-fx/docs/tiff6.pdf), [CIPA Exif 2.3](https://www.cipa.jp/std/documents/e/DC-008-2012_E_C.pdf)
- EXIF Orientation is `SHORT`, count 1 in IFD0; PixelXDimension/PixelYDimension are `SHORT` or `LONG`, count 1 in the Exif IFD. Missing tags should remain missing—adding entries would require rebuilding IFDs and risks MakerNote offsets. — Source: [CIPA Exif 3.1/current standards](https://www.cipa.jp/e/std/std-sec.html)
- Safe XMP mutation is not a regular-expression problem. Namespace aliases, attribute/element forms, RDF containers, entity references, and Extended XMP make text substitution ambiguous. A namespace-aware XML parser/tokenizer is required; otherwise transformed output must drop XMP. — Source: [Adobe XMP specifications](https://developer.adobe.com/xmp/docs/xmp-specifications/), [XMP Part 3](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/docs/XMPSpecificationPart3.pdf)
- `DOMParser.parseFromString()` is a Trusted Types sink even for XML. Therefore “CSP/Trusted Types are not involved” is true only for a dedicated byte parser; it is not true if browser XML parsing is used. — Source: [MDN DOMParser](https://developer.mozilla.org/en-US/docs/Web/API/DOMParser/parseFromString), [HTML Standard](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html)
- Extended XMP is not safely copyable after relevant edits unless every chunk is reassembled and validated, edited, reserialized, re-chunked, and its MD5-derived GUID and `xmpNote:HasExtendedXMP` value updated. — Source: [XMP Part 3](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/docs/XMPSpecificationPart3.pdf)
- EXIF and JFIF both require their application marker immediately after SOI—APP1 for EXIF, APP0 for JFIF—so a hybrid file cannot strictly satisfy both. Adobe recommends EXIF, XMP, Photoshop resources, then other markers. — Source: [CIPA Exif 3.1](https://www.cipa.jp/e/std/std-sec.html), [JFIF 1.02](https://www.w3.org/Graphics/JPEG/jfif.pdf), [XMP Part 3](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/docs/XMPSpecificationPart3.pdf)
- Do not copy the original ICC APP2, but do retain an ICC APP2 produced by the new canvas encoder. The HTML Standard requires serialized formats that support color profiles to identify the canvas color space. Untagged images are treated as sRGB on the web, but not necessarily by every desktop/print workflow. — Source: [HTML canvas specification](https://html.spec.whatwg.org/multipage/canvas.html), [CSS Color 4](https://www.w3.org/TR/css-color-4/)
- Already-compliant ordinary JPEGs in `keep-no-gps`, `copyright`, or `none` should be rewritten losslessly at the marker level, preserving scan/entropy bytes. Re-encoding would add needless generation loss. Special JPEGs—MPF/MPO, gain maps, C2PA, trailing secondary images—must remain exact passthrough or be rejected/custom-processed. — Source: analysis
- The owner’s `keep` default is a material privacy choice: it preserves GPS by design. Cloudflare documents that its `keep` setting retains GPS, although Cloudflare’s own current default is `copyright`, not `keep`. — Source: [Cloudflare Images metadata](https://developers.cloudflare.com/images/optimization/features/)
- Current local behavior is not yet a job queue: the upload dialog assigns `td-dropzone.upload`, every accepted row starts immediately, `upload.maxSize` rejects the original before processing, and failed rows have no retry action. — Source: local project analysis

### Considerations

- **EXIF segment validation:** accept exactly one `Exif\0\0` APP1 for transformed preservation. Multiple EXIF APP1 segments are nonconforming/ambiguous; transformed `keep` drops all EXIF with a `metadata-invalid` warning, while exact `keep` passthrough leaves the original untouched. — Source: [CIPA Exif](https://www.cipa.jp/e/std/std-sec.html); analysis
- **Endianness and bounds:** require `II` or `MM`, TIFF magic 42, checked 32-bit arithmetic, in-bounds IFD counts/entries/value ranges, a visited-offset set, bounded IFD/entry counts, and no duplicate structural tags. Cycles, overflow, overlap, or out-of-bounds pointers invalidate the EXIF family. — Source: [TIFF 6.0](https://www.itu.int/itudoc/itu-t/com16/tiff-fx/docs/tiff6.pdf); analysis
- **Malformed metadata failure:** do not reject an otherwise decodable image merely because optional metadata is malformed. For a re-encode, omit the malformed family and report partial preservation. For a privacy-mode lossless rewrite, omit the whole suspect family; reject only if the JPEG container cannot be safely transcribed without risking a leak. — Source: analysis
- **Orientation patch:** for a transformed, orientation-normalized image, write Orientation 1 into the existing `SHORT`/count-1 inline slot using its original byte order. Missing Orientation is safe and remains absent; wrong type/count or duplicate values invalidate the EXIF family. — Source: [CIPA Exif 3.1](https://www.cipa.jp/e/std/std-sec.html)
- **Dimension patch:** update existing PixelXDimension and PixelYDimension in the Exif IFD. Support both `SHORT` and `LONG`, count 1; reject the EXIF family on unexpected representations. Do not add missing tags. Also normalize any existing IFD0 ImageWidth/ImageLength rather than leaving contradictory dimensions. — Source: [CIPA Exif 2.3](https://www.cipa.jp/std/documents/e/DC-008-2012_E_C.pdf); analysis
- **Other stale EXIF structure:** copying the segment requires an explicit patch/deny table for resolution, ColorSpace, ComponentsConfiguration, Interoperability entries indicating Adobe RGB, and Exif 3.x references to auxiliary/original-preservation data that is not copied. Unknown photographic tags may remain; unknown image-structure tags make the family unsupported. — Source: [CIPA Exif standards](https://www.cipa.jp/e/std/std-sec.html); analysis
- **Resolution conflict:** canvas serialization is conventionally 96 dpi, while copied EXIF and encoder JFIF may report different densities. Use the encoder’s JFIF density as authoritative and patch existing EXIF XResolution/YResolution/ResolutionUnit to agree; do not leave conflicting density declarations. — Source: [MDN `toBlob`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob), [JFIF 1.02](https://www.w3.org/Graphics/JPEG/jfif.pdf)
- **MakerNote:** keeping the entire EXIF segment at its original length preserves TIFF-relative and many vendor-relative MakerNote layouts. Never insert/remove bytes inside retained EXIF. This is best-effort because vendor MakerNote conventions are not standardized. — Source: [TIFF 6.0](https://www.itu.int/itudoc/itu-t/com16/tiff-fx/docs/tiff6.pdf); analysis
- **IFD1 thumbnail:** set IFD0’s next-IFD pointer to zero. Validate IFD1 and zero its referenced JPEG thumbnail or strip ranges in place before disconnecting it; do not truncate the APP1 because thumbnail/value data and MakerNote data may be interleaved. If safe non-overlapping zeroing cannot be proven, drop the EXIF family. — Source: [CIPA Exif](https://www.cipa.jp/e/std/std-sec.html); analysis
- **GPS removal:** set the IFD0 GPSInfo pointer to zero and zero the GPS IFD plus every validated external value range it references. Merely setting the pointer to zero leaves recoverable coordinates. Overlap with retained ranges invalidates the EXIF family. — Source: [CIPA Exif 2.3](https://www.cipa.jp/std/documents/e/DC-008-2012_E_C.pdf); analysis
- **Meaning of `keep-no-gps`:** remove standardized EXIF GPS, all XMP in v0.90, and IPTC legacy/location fields. It cannot prove that coordinates are absent from MakerNotes or free text. Report `gpsFieldsRemoved: true` but `gpsPresent: "unknown"` when opaque retained metadata exists; recommend `none` for the strongest privacy mode. — Source: [IPTC Photo Metadata Standard](https://iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html); analysis
- **APP1 size:** JPEG’s two-byte marker length includes the length field and excludes the marker, so an APP payload is at most 65,533 bytes. In-place EXIF editing does not grow the segment. Every rebuilt segment must be checked independently. — Source: [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf)
- **XMP v0.90 handling:** do not mutate XMP text in this release. Exact `keep` passthrough retains Standard and Extended XMP byte-for-byte; transformed images and selective metadata modes drop all XMP APP1 segments and report partial preservation. This avoids stale orientation/dimensions and broken Extended XMP GUIDs. — Source: analysis
- **Future XMP support:** if required, implement or adopt a namespace-aware parser that supports attribute and element properties, scoped prefixes, RDF containers, UTF-8 validation, duplicate/conflict detection, Extended XMP assembly, MD5 verification, and re-chunking. Never use regex-only replacement. — Source: [XMP Part 3](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/docs/XMPSpecificationPart3.pdf)
- **EXIF/XMP conflict:** in v0.90 there is no conflict after transformation because XMP is dropped and EXIF is normalized. On exact passthrough, preserve the original conflicts without choosing a winner. — Source: analysis
- **IPTC/APP13:** parse `Photoshop 3.0\0` and its big-endian `8BIM` resource blocks. Rebuild APP13 with only IPTC-NAA resource `0x0404`; omit Photoshop thumbnails `0x0409`/`0x040C`, embedded ICC `0x040F`, XMP resources, and unrelated Photoshop state. — Source: [Adobe Photoshop file-format specification](https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/)
- **IPTC modes:** `keep` retains validated IIM records; `keep-no-gps` removes all standardized location records; `copyright` retains only By-line/Creator `2:80` and Copyright Notice `2:116`; `none` drops APP13. Credit and Source are supply-chain fields and are not included in the deliberately narrow copyright allowlist. — Source: [IPTC Photo Metadata Standard](https://iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html); analysis
- **Malformed/oversized IPTC:** validate normal and extended IIM lengths and IRB padding. An individual resource that cannot fit a marker or a malformed resource causes the IPTC family to be omitted, not copied opaquely. — Source: [Adobe Photoshop file-format specification](https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/); analysis
- **Copyright mode:** retain EXIF Artist and Copyright plus the two IPTC fields above. XMP rights are not preserved in v0.90 because selectively extracting `dc:creator`, `dc:rights`, and `xmpRights:*` safely requires RDF parsing. — Source: [IPTC mappings](https://iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html); analysis
- **C2PA/JUMBF:** exact `keep` passthrough retains it. Any pixel re-encode or marker rewrite invalidates the hard binding unless a claim generator signs a new derivative, which this kit cannot do; therefore transformed or selective-mode output drops C2PA and reports `contentCredentials: "dropped-transform"`. Do not delete unrelated APP11 merely by marker number without identifying its JUMBF content. — Source: [C2PA specification](https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification)
- **MPF, MPO, Ultra HDR/gain map:** retain the earlier special-JPEG rule. Exact `keep` passthrough is allowed when compliant; if dimensions/bytes require transformation, reject or use a site processor. Do not silently flatten the primary image merely because the metadata splicer can drop MPF APP2. — Source: [Android Ultra HDR](https://developer.android.com/media/grow/ultra-hdr), [CIPA standards](https://www.cipa.jp/e/std/std-sec.html); analysis
- **Encoder markers:** parse the canvas JPEG but preserve its APP0/JFIF, APP2 ICC, APP14 Adobe, tables, scans, and any other encoder-owned structural markers. “Do not copy ICC/APP14” applies to the original file, not to newly generated encoder output. — Source: [HTML canvas specification](https://html.spec.whatwg.org/multipage/canvas.html); analysis
- **Marker order:** for transformed files, emit SOI → normalized EXIF APP1 → XMP APP1 if a future parser supports it → rebuilt IPTC APP13 → the encoder’s marker stream. This follows Adobe compatibility guidance but means an encoder JFIF APP0 is no longer strictly immediately after SOI; document the unavoidable EXIF/JFIF conflict and test consumers. — Source: [XMP Part 3](https://github.com/adobe/XMP-Toolkit-SDK/blob/main/docs/XMPSpecificationPart3.pdf), [JFIF 1.02](https://www.w3.org/Graphics/JPEG/jfif.pdf)
- **Browser output variance:** do not hard-code assumptions about JFIF, ICC, APP14, progressive/baseline output, or marker order. The HTML specification defines serialization behavior but not a fixed JPEG marker layout; inspect each returned blob and verify MIME and dimensions. — Source: [HTML canvas specification](https://html.spec.whatwg.org/multipage/canvas.html)
- **Size accounting:** create the metadata plan before the quality search. Every candidate is compliant only when the final assembled JPEG—including preserved MakerNote/IPTC and marker overhead—is `<= maxBytes`. Retain the smallest compliant assembled candidate; never compare only `toBlob().size`. — Source: analysis
- **Large metadata floor:** a 60 KiB MakerNote leaves correspondingly less room for pixels. Valid supported metadata requested by `keep` must not be silently discarded merely to meet `maxBytes`; if no final file fits, reject `cannot-satisfy-limits` with metadata overhead included in diagnostics. — Source: analysis
- **Lossless compliant-JPEG rewrite:** implement a full marker-aware transcriber through every scan and EOI, recognizing byte stuffing and restart markers. Selective policies may remove/rebuild APP/COM segments while copying entropy bytes exactly. Reject unexpected trailing data or special multi-image structure rather than leaking or corrupting it. — Source: [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf); analysis
- **Exact passthrough matrix:** `keep` returns the identical original when all limits pass. For the other modes, return the identical original only if inspection proves no mutation is required; otherwise use the lossless rewrite. This preserves hashes whenever possible. — Source: analysis
- **PNG resize:** keep PNG and alpha. Reinsert a validated, normalized PNG `eXIf` chunk using the same TIFF engine; copy only recognized safe metadata chunks. Drop XMP `iTXt` on transformed output in v0.90. Unknown unsafe-to-copy ancillary chunks must not survive pixel changes. — Source: [PNG Third Edition](https://www.w3.org/TR/png-3/); analysis
- **PNG selective passthrough:** losslessly omit whole chunks—no pixel re-encode. `none` drops eXIf, all text/time/XMP/C2PA metadata and unknown non-rendering ancillary chunks; `keep-no-gps` drops eXIf/XMP/location-bearing text conservatively; `copyright` keeps only validated `Author` and `Copyright` text. Preserve color/rendering and APNG chunks. — Source: [PNG Third Edition](https://www.w3.org/TR/png-3/); analysis
- **WebP/HEIC and other passthrough formats:** exact `keep` may upload them when every applicable limit passes. For `keep-no-gps`, `copyright`, or `none`, reject with `metadata-policy-unsupported` unless inspection proves the relevant metadata is absent or a site processor performs the rewrite. Never upload with only a warning because that violates the selected policy. — Source: [RFC 9649 WebP](https://www.rfc-editor.org/rfc/rfc9649.html); analysis
- **No `<img>` fallback:** if the `createImageBitmap` behavioral probe fails, reject transformations as `resize-unsupported`. Existing optional UI thumbnails in `td-dropzone[preview]` are separate from the decoder fallback and still require `img-src blob:` if a site enables them. — Source: [HTML ImageBitmap specification](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html); local project analysis
- **No kit numeric limits:** enabling resize should require sites to declare input safety caps and at least one output ceiling. Docs must use exact bytes and warn that frontend and backend values, inclusivity, and units must come from one site configuration. — Source: analysis
- **Current `maxSize` collision:** when resizing is enabled, the current raw `upload.maxSize` cannot remain the dropzone’s pre-upload ceiling. Split it into `maxInputBytes` for admission and `maxBytes` for the processed result; legacy `maxSize` behavior remains only when processing is disabled. — Source: local project analysis
- **Server boundary:** Symfony/PHP must still sniff type, decode safely, enforce dimensions and bytes, and apply the site’s authoritative metadata/privacy policy. Client metadata reporting is advisory and can be bypassed; many CMS/image pipelines may strip it again. — Source: [OWASP File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
- **Adapter information:** include `metadataPolicy`, `metadataOutcome: "exact"|"preserved"|"partial"|"stripped"|"unsupported"`, `metadataFamilies`, `gpsFieldsRemoved`, `gpsPresent: true|false|"unknown"`, `contentCredentials`, and special-content outcome in `optimization`. Do not claim what the server ultimately stored. — Source: analysis
- **Queue:** use one module-global FIFO optimization slot across picker/dropzones; cancellation removes queued jobs. Uploads may overlap independently while the next image optimizes. Hold only original `File` references until a job starts. — Source: analysis
- **Job state:** `queued → optimising → uploading → done|error|cancelled`. Optimization stays indeterminate; upload alone gets numeric progress. A close confirmation must consider queued and optimizing jobs busy, not just `td-dropzone.uploading`. — Source: local project analysis
- **Retry:** retain a successful processed `File` and its optimization envelope after upload failure, so retry repeats only the adapter call. An optimization failure retries the bounded optimization from the original. Snapshot upload fields when the job is admitted so queued files do not observe later form edits. — Source: analysis
- **`td-dropzone`:** add an opt-in `processor(file, {signal,onPhase})` property and pass `originalFile` plus `optimization` to its existing upload hook. It must never inherit picker defaults implicitly. Add queued/optimising states and a retry action while preserving the old behavior when no processor exists. — Source: analysis
- **Accessibility:** mark the active row/list busy, expose phase text, give cancel/retry buttons file-specific names, keep optimization progress indeterminate, debounce live announcements, restore focus after remove/retry, and respect reduced motion. — Source: analysis
- **URL uploads:** remain server-owned and do not enter the browser resize queue. The server must apply the same limits and metadata policy to remote URLs. — Source: local project analysis
- **Release boundary:** v0.90 contains the shared processor, global queue, metadata envelope, dialog integration, retry/cancel, and adapter contract. v0.91 reuses that model for grid drop; it should not introduce a second queue or policy implementation. — Source: analysis

### Recommendations

- Adopt the following consolidated policy semantics:

  - `keep`: exact passthrough when compliant; on JPEG/PNG transformation preserve validated EXIF/eXIf and IPTC as specified, including EXIF GPS; drop XMP/C2PA and report partial preservation.
  - `keep-no-gps`: losslessly remove standardized EXIF, IPTC, PNG, and XMP location metadata; retain other supported metadata; document that opaque/free-text fields can make actual GPS presence unknown.
  - `copyright`: rebuild minimal EXIF Artist/Copyright plus IPTC By-line/Copyright Notice and PNG Author/Copyright; drop XMP in v0.90.
  - `none`: retain only rendering/structural information such as encoder ICC, JFIF, Adobe transform markers, PNG color/animation chunks; remove other metadata.
- Treat metadata preservation as best-effort only for malformed optional metadata: strip the invalid family and expose `partial`. Valid supported metadata requested by `keep` is part of the final byte budget and must not be silently removed to satisfy `maxBytes`.
- Preserve special JPEG content only through exact passthrough. Reject required transformations of MPF/MPO, Ultra HDR/gain-map, C2PA-sensitive, or trailing-image JPEGs unless a site supplies an explicit processor.
- Implement lossless marker/chunk rewriting for already-compliant ordinary JPEG and PNG. Do not force generation loss merely to remove metadata.
- Add stable errors: `metadata-invalid`, `metadata-too-large`, `metadata-policy-unsupported`, and `special-content-transform-required`.
- Add fixtures covering:

  - EXIF orientations 1–8 in both byte orders.
  - `SHORT`/`LONG` dimensions, missing/duplicate/wrong-type tags.
  - MakerNote, GPS, JPEG and uncompressed IFD1 thumbnails.
  - Cyclic/overlapping/out-of-bounds IFDs and boundary-sized APP1.
  - Multiple EXIF APP1, Standard/Extended XMP, IPTC IIM and Photoshop thumbnail/ICC resources.
  - JFIF+EXIF ordering, encoder ICC/APP14, progressive multi-scan JPEG.
  - MPF/MPO, gain map, C2PA, trailing data.
  - PNG eXIf, XMP iTXt, text metadata, APNG and unknown safe/unsafe chunks.
  - A 60 KiB MakerNote under a tight `maxBytes`.
  - Queue cancellation at every await boundary and upload retry without a second encode.

- Run behavioral tests in Chromium, Firefox, and Playwright WebKit, asserting decoded pixels, dimensions, MIME, marker/chunk invariants, entropy preservation for lossless rewrites, privacy outcomes, final byte ceilings, abort races, and adapter metadata—not byte-identical browser encodes.
- Document the `keep` GPS risk next to the option and in the upload integration guide, not only in a privacy appendix.

### Open Questions

- **OWNER DECISION:** accept the recommended v0.90 scope in which transformed/selective output drops XMP, including Extended XMP, and reports partial preservation. Preserving or selectively filtering XMP safely would require a dedicated namespace-aware RDF/XML parser and materially enlarge v0.90. Recommendation: defer XMP mutation/preservation to a later release or a site-supplied processor.
